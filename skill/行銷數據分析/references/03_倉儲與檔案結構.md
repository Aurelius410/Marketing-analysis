# 倉儲與檔案結構

這份文件回答一個問題：**這次分析產生的每一個檔案，該叫什麼名字、放在哪裡、由誰產生、可以被誰讀。** 它看起來是行政規範，實際上是整套 skill 裡最便宜的防呆——因為結構錯誤造成的損失，永遠是在最後一哩才被發現的。

漏掉這裡的規則會發生什麼，都有實證可循：分區粒度亂訂會讓 7,764 列的課程資料集被切成 192 個小檔，查詢規劃時間超過掃描時間（見 §二）；用 `APPEND` 做日常載入會讓重跑必然重複灌資料（18-T7）；欄名映射沒做，`smf.ols('刷卡金額 ~ 年齡')` 會在 patsy 的識別字解析上直接爆掉（§三）；`expire_snapshots` 清掉了被報告引用過的 snapshot，「半年後能重跑出同一份數字」就是空話（§六）。最貴的一條是 `union_by_name` 遇到欄位改名——它會靜默拆成兩欄各半 NULL，`SUM(spend)` 少算一半，ROAS 從真實的 1.6 算成 3.2，然後你會建議把預算加倍投進一個剛好打平的活動，而**全程沒有任何一行報錯**。

結構的紀律和分析的紀律是同一件事：**每階段都留成果、絕不覆寫**（SKILL 紀律 2）。這份文件只是把那條紀律落成資料夾與檔名。

## 一、專案資料夾結構

### 1.1 三段式的來源

包子自己的 Excel 檔已經是這個形狀了。HW2 的 14 張工作表順序是 `客戶資料檔 → 產品資料檔 → 交易記錄檔 → Step 1 → Step 2 → Step 3 → Pivot → WMLE & CAI → 活躍&非活躍分群描述`（出處：`gdrive/own/02_包子自己的計算檔逐步拆解.md` §2.1）。素材的評註講得很準：「他把百分位這種可以直接內嵌到 IF 裡的中間值獨立成欄，把參數表獨立成工作表，把三法比較再獨立成一張表」——**每一個可驗證的中間量都存成看得見的欄或表**（同上 §1.2 評註）。

抽出來就是三段：

| 段 | Excel 裡長什麼樣 | 資料夾對應 | 硬規則 |
|---|---|---|---|
| **原始段** | `客戶資料檔` / `交易記錄檔` 分頁，從不編輯 | `原始資料/` | 唯讀，寫入即凍結 |
| **加工段** | `Step 0_1` → `Step 4`，一步一張表，不覆寫前一步 | `清理後資料/` `分析資料表/` `顧客特徵表/` `模型輸出/` | 每步可獨立檢查，可整段重跑 |
| **呈現段** | `Pivot`、`分群描述`、`三法比較` | `統計表/` `圖表/` `交付物/` | 只呈現，不在這裡算新數字 |

### 1.2 完整結構

資料夾名稱**不帶數字編號、用完整名稱**——數字編號在 Excel 分頁上有用（強制排序），在檔案總管裡只會讓你記不住 `05` 是模型還是圖表。所以**這份 skill 裡不存在 `01_raw/`、`04_features/`、`06_figures/`、`07_report/` 這類編號式英文目錄**；看到就是筆誤，對照表在下面這棵樹（raw→`原始資料/`、staging→`清理後資料/`、mart→`分析資料表/`、features→`顧客特徵表/`、models→`模型輸出/`、figures→`圖表/`、report/delivery→`交付物/`、intake→`開案與問題定義/`、log→`執行紀錄/`、quarantine→`隔離區/`）。`verify_outputs.py` 要帶一條靜態 CHECK：references 與腳本裡不得出現 `0N_英文名/` 形式的硬編路徑，路徑一律走 `from paths import project_dir`。

下面這棵樹是 `scripts/paths.py` 的 `PROJECT_SUBDIRS` / `FIGURE_SUBDIRS` / `TABLE_SUBDIRS` 的鏡像——`project_dir()` 真的會把它們建出來，兩邊不一致就是 bug（見 §八維護條款）。**`統計表/` 的七類與 `圖表/` 的九類都是按「分析模組」分，不是按「圖種」分**；按圖種（分布／關係／時間趨勢／組成占比／排行比較）的那條軸線是選圖用的決策軸，住在 19 §4.1，不是目錄結構。

### 1.3 `圖表/報告用/` 的規則：複製，絕不重畫

**報告裡出現的每一張圖，都必須是某個分析階段已經產出、已經被檢查過的圖的複製品。** 不准為了報告重畫一張「比較好看的版本」。

理由是 18-E7：學生E的報告圖例標「女 75.20%、男 24.80%」，內文卻寫「女性佔 24.8%」，**內文與圖完全相反**。重畫的那一刻，你就製造了第二個數字來源，而兩個來源遲早會不一致。同樣的道理適用於「報告用的圖字要大一點」——那是改樣式，改樣式要回去改 `build_chart()` 然後重跑全部，不是在報告資料夾裡另存一個。

**實作只有一份，在 19 §6.2 的 `scripts/collect_figures.py`**（複製時保留原檔名、寫出含 sha256 的 JSON manifest，`verify_outputs.py` 的四條檢查也綁在那個形狀上，`20_交付物產製.md` §3.2 的 `build_report.py` 就是讀它）。這裡只寫規則與理由，不要在這一節另寫一支 script——同一件事寫兩邊，遲早只改一邊（見 §八維護條款第 3 條）。報告圖編號的需求併進 19 那份 manifest 的欄位，不要為它另立一支收圖工具。

## 二、DuckDB + Parquet + DuckLake 的分層實作

### 2.1 三層的職責邊界

出處：`research/01_warehouse_sql_parquet.md` §3.1。

| 層 | 資料夾 | 允許做的事 | **禁止**做的事 | 格式 |
|---|---|---|---|---|
| **raw** | `原始資料/` | 型別一律最寬鬆（**全 VARCHAR**）、加 `_ingested_at` / `_source_file` / `source_tz` | 任何商業邏輯、任何 JOIN、任何過濾、任何型別轉換 | Parquet + zstd |
| **staging** | `清理後資料/` | 型別轉換、欄名映射成 snake_case、去重、時區正規化、bot 標記、哨兵值處理 | 跨資料源 JOIN、任何聚合 | Parquet + zstd |
| **mart** | `分析資料表/` | 跨源 JOIN、聚合、指標計算、SCD2 | 回頭改 raw／staging | **DuckLake** |

**raw 為什麼全 VARCHAR**：型別轉換全部延到 staging，上游型別怎麼變都不會炸掉 raw 的實作（research/01 §5.1）。代價是 staging 的 cast 可能靜默失敗，所以必須配一條 `checks/stg_*__cast_loss.sql`（見 §四 W6）。

**為什麼 raw/staging 用純 Parquet、mart 才用 DuckLake**：raw 與 staging 是「重跑就整段重建」的，不需要交易與 snapshot；mart 是「增量累積、會被報告引用、重跑不能重複灌」的，正好需要 `MERGE INTO` + snapshot（research/01 §3.1）。DuckLake 規格 1.0 是 2026 年 4 月才發佈的新格式，**先在 mart 試點，不要三層一起上**。

### 2.2 Parquet 寫入的固定參數

壓縮一律 **zstd**。不是 snappy（壓縮率差太多），不是 gzip（解壓慢）。

```sql
COPY (SELECT ...) TO '清理後資料/stg_orders'
(FORMAT parquet, COMPRESSION zstd, PARTITION_BY (year, month), OVERWRITE_OR_IGNORE);
```

### 2.3 分區策略：決策表，不是固定值

**藍圖 §S3 曾把分區寫死成「依年月」，那是錯的**（出處：`gap-data-engineering.md` N1）。課程資料集 7,764 列若按年月分割 → 24 個分區、每個約 30 KB；再加上 DuckDB 官方明述「one file is written per thread to each directory」，8 核心會在每個目錄產生最多 8 個檔 → **最多 192 個小檔**。而 raw 讀取又必須加 `union_by_name = true`（要讀所有檔案的 metadata 才能建立聯集 schema）→ 查詢規劃時間可能超過實際掃描時間。

判準是**查詢模式 + 100 MB 門檻**，不是資料量本身。DuckDB 官方 `partitioned_writes` 頁面的 Bestpractice 原文：「Writing data into many small partitions is expensive. It is generally recommended to have at least 100 MB of data per partition.」（research/01 §3.3）

```
這批資料要不要分區？
│
├─ 全年總量 < 幾百 MB ───────────────────→ 不分區，單一 parquet
│
├─ 查詢不會固定帶某一欄的範圍條件 ───────→ 不分區
│                                          （靠 row group 的 min/max 統計 pruning 就夠）
└─ 查詢幾乎每次都帶同一欄的範圍條件（通常是日期）
   │
   └─ 單一分區的預估大小是多少？
      ├─ < 100 MB ──→ 往上退一級（day → month → year），退到過門檻為止
      ├─ 100 MB–1 GB → 就用這一級
      └─ > 1 GB ────→ 再細一級（year → year/month → year/month/day）
                       但**最細只到 day=，禁止 hour=**
```

四種資料的預設答案（research/01 §3.3，數字是該文的估算，不是量測值）：

| 資料型態 | 年資料量級 | **分區粒度** | 理由 |
|---|---|---|---|
| CRM 交易（百萬列） | ~200 MB | **不分區**，單一 parquet | 全年還不到 100 MB × 2，分了只產生小檔 |
| 廣告投放成效 | ~50 MB | **不分區** | 通常是日彙總，量極小 |
| 零售 POS（千萬列） | ~2 GB | **`year=/month=`** | 每月約 170 MB，剛好過門檻 |
| 網站行為事件（上億列） | ~20–50 GB | **`year=/month=/day=`** | 每日約 60–140 MB 符合門檻，且查詢幾乎都帶日期範圍 |

**禁止 `hour=`**：每小時 3–6 MB，遠低於官方 100 MB 建議值。

兩個實作細節要一起記：`partitioned_write_max_open_files` **預設 100**，分區數多時要調高（代價是記憶體）；分區數 × threads 就是檔案數，8 核心 × 365 天 = 2,920 個檔，在 Windows 上會很痛。

**S3 回報時必須說明「本專案為什麼選這個粒度」**，不能只寫「依年月分區」。事件資料另有一條：量大的事件永遠**留在 Parquet 用 VIEW 暴露**，不灌進 DuckDB 原生表——分區裁剪讓「留在檔案裡」幾乎沒有代價，灌進去反而失去這個好處還讓 `.duckdb` 膨脹到難以備份（research/01 §4.1）。

```sql
CREATE OR REPLACE VIEW ev_web_event AS
SELECT * FROM read_parquet('清理後資料/stg_web_event/**/*.parquet',
                           union_by_name = true, hive_partitioning = true);
ATTACH 'ducklake:warehouse/marketing.ducklake' AS mart (DATA_PATH 'warehouse/mart_data/');
```

## 三、命名規約

### 3.1 中文的邊界線（最容易延伸出錯的一條）

專案根目錄本身很可能含中文（這個 Skill 的開發環境就是），而教材的欄名也全是中文（`客戶ID`、`刷卡金額`、`刷卡產品產業分類`）。這個習慣**極容易延伸到 partition value**，寫出 `store=台北信義店` 這種目錄——然後在某個工具鏈上炸掉，而且不會告訴你為什麼（出處：`gap-data-engineering.md` N1）。

| 位置 | 中文？ | 理由 |
|---|---|---|
| 專案根目錄 `行銷分析\` | ✅ 既成事實 | DuckDB/Python 內部用 UTF-8，research/01 §10.2 判斷可行 |
| 章節資料夾（`統計表/`、`圖表/報告用/`） | ✅ 允許 | 人在檔案總管裡導航用的，不出現在 glob wildcard 之下 |
| **資料集目錄名**（`stg_orders/`、`source=crm_orders/`） | ❌ **禁止** | 這一層以下是 DuckDB 用 `**` 掃的範圍 |
| **partition key 與 value**（`store_id=T001`） | ❌ **禁止** | 目錄名會進 URL encode 邏輯；用代碼，中文名放維度表 JOIN 回來 |
| **Parquet 檔名** | ❌ **禁止** | 全小寫底線 + ASCII |
| **欄位名** | ❌ **禁止** | 見 §3.3 |
| 統計表 / 圖表 / 交付物的檔名 | ✅ 允許 | 給人看的產出，不被程式 glob |

> ⚠️ **未查證項，開案第一天要處理**：research/01 §13 第 9 條誠實列出「DuckDB 在 Windows 上的中文路徑行為，我沒有實際測試」。所以**開案第一件事跑一個 5 分鐘的冒煙測試**：在 `原始資料/` 底下寫一個 parquet、用 glob 讀回來、比對列數。過了就照上表走；沒過就把資料三層改成 ASCII 別名（`raw/` `staging/` `mart/`），章節資料夾維持中文。**不要靠推論，跑一次就知道。**

### 3.2 表名與檔名

一律**全小寫、底線分隔**。理由是 Windows 檔案系統大小寫不敏感、但 Parquet 內的欄位名大小寫敏感，混用必踩雷（research/01 §3.2）。

| 前綴 | 層 | 範例 | 粒度寫在哪 |
|---|---|---|---|
| `raw_` | raw | `raw_pos_txn` | 契約檔 `contracts/pos.yml` 的 `grain` |
| `stg_` | staging | `stg_orders`、`stg_web_event` | 同上 |
| `fct_` | mart 事實 | `fct_transaction`、`fct_marketing_spend` | 表註解第一行 |
| `dim_` | mart 維度 | `dim_customer`、`dim_store`、`dim_fx_rate` | 一自然鍵一列（SCD2 則加 `valid_from`） |
| `map_` | mart 對照 | `map_identity`、`dim_channel_mapping` | — |
| `feat_` | 特徵 | `feat_rfm`、`feat_cai` | 一顧客一列 + `as_of_date` |
| `log_` | 治理 | `log_measurement_change`、`ingest_watermark` | — |

檔名 = 表名。`SQL/models/stg_orders.sql` 產出 `stg_orders`，一對一，不准一支 SQL 建三張表。

### 3.3 欄名映射：中文欄名不准進 staging

**staging 一律把欄名映射成 snake_case ASCII，中文顯示名放 `dim_column_label`。**

不做的具體後果：`smf.ols('刷卡金額 ~ 年齡', data=df)` 這種 formula 會在 patsy 的識別字解析上出問題（出處：`gap-data-engineering.md` N1）。而 formula 介面是 ANOVA、迴歸、事後檢定的共同入口——這一條漏掉，M7 整段都要用 workaround 硬幹。

映射表本身是資料，不是程式裡的 dict：

```sql
-- dim_column_label：報告輸出時把 snake_case 換回中文
CREATE OR REPLACE TABLE dim_column_label (
    table_name    VARCHAR,        -- 'feat_rfm'
    column_name   VARCHAR,        -- 'm_net_twd'
    label_zh      VARCHAR,        -- '淨消費金額'
    unit          VARCHAR,        -- 'TWD' / 'ratio' / 'days'
    grain         VARCHAR,        -- 'txn' / 'customer_day' / 'item'
    definition_id VARCHAR         -- 指向指標字典（見 18-G10）
);
```

| 原始中文欄名 | staging 欄名 | 為什麼不是別的 |
|---|---|---|
| 客戶ID | `customer_id` | 顧客單位一律 `customer_id`，`card_id` 只能當工具維度 |
| 刷卡金額 | `amount_twd` | 金額欄一律帶幣別後綴 |
| 刷卡日期 | `txn_date` | 日期語意欄不叫 `date` |
| 交易筆數 | `f_txn_cnt` | **禁止裸 `F`**——三種粒度差 23%（見 ref 17 §二） |
| 消費天數 | `f_active_days` | 同上 |
| 刷卡產品產業分類 | `category_l1` | 層級用 `_l1`/`_l2`，不用中文層級名 |

其他固定規則：金額型別一律 `DECIMAL(18,4)`，**禁止 `DOUBLE`/`FLOAT`**（`gap-data-engineering.md` D17）；率欄位一律存 `ratio`（0.0235），只在呈現層乘 100，契約檔的每個率欄位必填 `unit: ratio|percent`（同上 D3）；欄位名不要有斜線（官方要求 url_encode，直接避免）。

## 五、SQL 撰寫慣例

### 5.1 檔案組織

```
SQL/
├── models/                     一支 SQL 建一張表，檔名 = 表名
│   ├── stg_orders.sql
│   ├── fct_transaction.sql
│   └── mart_customer_monthly.sql
├── checks/                     一支 SQL 一條斷言，回傳「違規列」，0 列 = 通過
│   ├── stg_orders__pk_unique.sql
│   ├── stg_orders__cast_loss.sql
│   └── feat_rfm__source_filter.sql
└── _schema_changes.sql         所有 ALTER TABLE 按時間 append，永不修改既有行
```

`checks/` 的檔名用 `<表名>__<檢查名>.sql` 雙底線分隔，讓 runner 可以直接從檔名知道這條檢查屬於哪張表。斷言 helper 只有 20 行（research/01 §6.2）：

```python
def check(con, name: str, sql: str):
    """sql 應回傳「違規列」；回傳 0 列 = 通過。"""
    n = con.execute(f"SELECT count(*) FROM ({sql})").fetchone()[0]
    if n > 0:
        sample = con.execute(f"SELECT * FROM ({sql}) LIMIT 5").fetchdf()
        raise AssertionError(f"[{name}] 有 {n} 列違規\n{sample}")
```

### 5.2 每支 SQL 的檔頭：這支在做什麼、輸入是誰、輸出是誰

**沒有檔頭的 SQL 不准進 `models/`。** 這不是文件潔癖——純 SQL runner 放棄了 dbt 的 `ref()` lineage（research/01 §8.3 誠實列出），檔頭的 `depends_on` 就是唯一的血緣來源，而且是 `scripts/build_lineage.py` 掃描的對象。

```sql
-- ============================================================
-- 檔名   : mart_customer_monthly.sql
-- 做什麼 : 把訂單聚合成「顧客 × 月」的事實表，供 M8 顧客價值與 M11 sizing 使用
-- 輸入   : stg_orders（粒度：一筆訂單一列）
--          dim_customer（粒度：customer_key + valid_from，SCD2）
-- 輸出   : mart.fct_customer_monthly（粒度：customer_key × month_start）
-- 口徑   : m_net_twd = 淨額（txn_type='sale'），記在**原交易日**（restatement 政策）
--          月份切法 = biz_date 的月，不是 calendar_date
-- depends_on: stg_orders
-- depends_on: dim_customer
-- 最後更新: 2026-07-26
-- ============================================================
```

四行必填欄位對應的是真實事故：沒有「口徑」那一行，`F` 用筆數還是天數半年後沒人記得（差 23%，ref 17 §二）；沒有「輸出粒度」那一行，JOIN 完列數暴增不會有人察覺。

### 5.3 CTE 風格

| 規則 | 為什麼 |
|---|---|
| **一個 CTE 只做一件事**，命名用名詞短語（`orders_filtered`、`customer_first_txn`） | `a`、`b`、`t1` 在 debug 時要往回捲三次才知道是什麼 |
| **由上而下**：來源 → 過濾 → 計算 → 聚合 → 最終 SELECT | 讀的順序 = 資料流動的順序 |
| **最終 SELECT 不做計算**，只挑欄位與排序 | 最後一段是「這張表長什麼樣」的宣告 |
| **禁止 `SELECT *`**（raw 實作除外） | 上游加一欄就會靜默改變下游 schema |
| 每個 `JOIN` 註明預期基數（`-- 1:1` / `-- 1:N`） | JOIN 後列數暴增是最常見的沉默錯誤 |
| 超過 5 個 CTE 就該拆成兩張表 | 拆了才能中間檢查（SKILL 紀律 2） |

### 5.4 註解規約

註解寫**為什麼**，不寫**做什麼**。`-- 計算平均值` 是噪音，`-- 用中位數不用平均，因為金額右偏且已知有 3% 大額企業戶` 才是資訊。

三種必寫的註解：

| 標記 | 用在哪 | 範例 |
|---|---|---|
| `⚠️` | **不可省的 WHERE / 過濾條件** | `AND txn_type = 'sale'  -- ⚠️ 不可省：退貨列會污染 R，見 ref 17 §二` |
| `-- 出處:` | 任何門檻、切點、權重 | `WHERE session_events <= 480  -- 出處: p99.9 of stg_web_event 2026H1` |
| `-- TODO(日期):` | 已知的暫時作法 | `-- TODO(2026-08-15): 幣別暫用 TWD，dim_fx_rate 建好後改 spend_twd` |

完整範本：

```sql
-- ============================================================
-- 檔名   : feat_rfm.sql
-- 做什麼 : 以 as_of_date 為基準計算 RFM 三指標
-- 輸入   : fct_transaction（粒度：一筆交易一列）
-- 輸出   : feat_rfm（粒度：一顧客一列 + as_of_date）
-- 口徑   : f_txn_cnt=筆數、f_active_days=消費天數，兩者並存不可混用
-- depends_on: fct_transaction
-- ============================================================
WITH txn_scoped AS (
    -- ⚠️ 兩個過濾都不可省，漏掉的後果完全不同：
    --    as_of_date  → 目標洩漏（18-G4），驗證集 AUC 0.95 上線崩盤
    --    txn_type    → 退貨列污染 R（ref 17 §二），一年沒買的人進冠軍名單
    SELECT customer_id, biz_date, amount_twd
    FROM fct_transaction
    WHERE biz_date <= DATE '2012-12-01'
      AND txn_type = 'sale'
),
agg AS (
    SELECT
        customer_id,
        DATE_DIFF('day', MAX(biz_date), DATE '2012-12-01') AS r_days_since_last_sale,
        COUNT(*)                        AS f_txn_cnt,
        COUNT(DISTINCT biz_date)        AS f_active_days,
        SUM(amount_twd)                 AS m_net_twd
    FROM txn_scoped
    GROUP BY customer_id
)
SELECT
    customer_id, r_days_since_last_sale, f_txn_cnt, f_active_days, m_net_twd,
    DATE '2012-12-01' AS as_of_date          -- 基準日入表，讓每一列都能自證口徑
FROM agg;
```

## 六、idempotency 與可重現

### 6.1 三層的 idempotency 機制

出處：research/01 §7。

| 層 | 機制 | 寫法 | 重跑保證 |
|---|---|---|---|
| raw / staging | **分區覆寫** | `OVERWRITE_OR_IGNORE` + 明確日期範圍 | 取代該範圍的分區，不累加 |
| mart | **`MERGE INTO`**（DuckLake 不支援 primary key，官方指定用這個） | `WHEN MATCHED THEN UPDATE WHEN NOT MATCHED THEN INSERT` | 同 key 的列被 UPDATE 而非再 INSERT |
| API 來源 | dlt 的 `write_disposition="merge"` + `primary_key` | state 存在 destination 的 `_dlt_*` 表 | 自動接續上次跑到哪 |

### 6.2 兩個自我檢查（第一次建 pipeline 時就要跑）

**檢查一：跑兩次結果應相同。**「這比任何框架的保證都實在」（research/01 §7.4）。

```python
before = con.execute("SELECT count(*), sum(m_net_twd) FROM mart.fct_transaction").fetchone()
run_pipeline()                    # 同樣的區間再跑一次
after  = con.execute("SELECT count(*), sum(m_net_twd) FROM mart.fct_transaction").fetchone()
assert before == after, f"非 idempotent！{before} -> {after}"
```

**檢查二：上游硬刪一列後重跑。** 這條 research/01 沒有，是缺口審查補的（`gap-data-engineering.md` D20）。

`MERGE INTO` **只 upsert、不刪除**。上游硬刪的列會在 mart 變成**幽靈資料**：電商取消訂單若上游直接刪列，mart 會累積 3% 的幽靈訂單 → 月營收高估 3%，而且**被取消訂單的顧客會一直留在 Champions 名單裡拿 VIP 禮**。

```python
# 模擬上游硬刪：從 staging 拿掉一筆，重跑 mart，mart 應該也要少一筆
con.execute("CREATE OR REPLACE TABLE stg_orders AS SELECT * FROM stg_orders WHERE order_id <> 'X001'")
run_pipeline()
assert con.execute("SELECT count(*) FROM mart.fct_transaction WHERE order_id='X001'").fetchone()[0] == 0, \
       "幽靈資料：上游已刪，mart 還在"
```

處理方式二選一：

| 上游會不會硬刪列？ | 做法 |
|---|---|
| **會**（電商取消訂單直接刪、CRM 刪除會員） | 該來源改用**分區全量取代**，不用 MERGE |
| **不確定** | 保留 MERGE，但加 `checks/mart__orphan_vs_staging.sql` 比對 key 集合差異，發現差異即 error |
| **不會**（只 append 的日誌型來源） | MERGE 即可 |

### 6.3 版本三件套：`run_id` / `snapshot_id` / `git_commit`

**每份交付物的 header 都要埋這三個。** HTML 報告放頁尾與 HTML 註解，Excel 放 `_meta` 工作表，儀表板放頁腳。

不埋的具體後果（`gap-data-engineering.md` D20）：報告寫「Champions 20 人、營收占比 48.6%」，兩週後主管要求重跑得到「19 人、47.2%」。期間發生了三件事——補載兩天遲到的 POS 資料、修了一條退貨規則、Meta 回填改了 7 月 spend。**沒有任何機制能說出是哪一項造成 1.4 個百分點的差異**，於是結論變成「這套系統的數字會漂」，此後每一個數字都要被重新質疑。

```json
// 執行紀錄/run_manifest.json（每次執行 append 一筆）
{
  "run_id": "2026-07-26T14:03:11_a91f",
  "git_commit": "3f2b9c1",
  "python": "3.14.1",
  "packages": {"duckdb": "1.5.5", "pandera": "0.32.1"},
  "metric_definitions_version": "v3",
  "inputs": [
    {"table": "mart.fct_transaction", "snapshot_id": 118,
     "row_count": 5294, "fingerprint_sum": 15026344.0000}
  ],
  "outputs": [
    {"path": "交付物/完整報告.html", "sha256": "8c1d…"},
    {"path": "統計表/行銷分析/rfm_分群摘要.csv", "sha256": "b47a…"}
  ]

```

配一支 `scripts/diff_runs.py`：比對兩個 `run_id`，**自動歸因**差異到「輸入資料變動」（snapshot_id 或指紋不同）／「程式邏輯變動」（git commit 不同）／「口徑變動」（字典版本不同）。DuckLake 的 `ducklake_table_insertions('mart','main','fct_transaction', 3, 4)` 直接接上就能列出哪幾列變了（research/01 §7.5）——這是現成能力，只是沒人包成工具。

### 6.4 `protected_snapshots`：兩份定案文件互相拆台的地方

這是一個必須明寫的衝突（`gap-data-engineering.md` D20）：

- S8 承諾「環境快照與資料指紋，確保**半年後能重跑出同一份數字**」。
- research/01 §4.4 引用官方明述「DuckLake **never deletes old data files**」，並建議定期 `expire_snapshots` + cleanup，「否則磁碟會被吃光」。

**兩份都對，放在一起就是：一旦 expire 了被報告引用的 snapshot，S8 的承諾就是空話。**

規則：**任何被 `run_manifest.json` 引用過的 snapshot 自動加入 `protected_snapshots` 清單，`expire_snapshots` 一律排除它們。** 這條邏輯固定在 `scripts/maintain_ducklake.py` 裡，不要靠人記得。

```python
# scripts/maintain_ducklake.py 的核心
protected = {inp["snapshot_id"] for run in load_manifest() for inp in run["inputs"]}
all_snaps = {r[0] for r in con.execute("FROM ducklake_snapshots('mart')").fetchall()}
expirable = sorted(all_snaps - protected)
# 只 expire 沒被任何交付物引用過的
# expire 是全域表函式 ducklake_expire_snapshots('<catalog>', ...)，沒有 catalog-scoped 形式；
# 寫成 mart.expire_snapshots(...) 會回 CatalogException【實測 duckdb 1.5.5 + ducklake】。
# 必須用 versions => 明列清單：older_than => 會忽略 protected 直接吃掉被引用的 snapshot。
con.execute("CALL ducklake_expire_snapshots('mart', versions => ?)", [expirable])
con.execute("CALL mart.merge_adjacent_files()")   # 這支反而有 catalog-scoped 形式，可以這樣寫（小檔合併，見 W12）
con.execute("CHECKPOINT")
```

### 7.1 `db.py` 連線範本

改寫自 research/01 §11.3，補上 `read_only` 分支與 encodings 一律載入。

```python
# scripts/db.py —— 所有腳本一律從這裡拿連線，禁止各自 duckdb.connect()
import duckdb
from pathlib import Path

from paths import project_dir            # scripts/paths.py，路徑不寫死

p    = project_dir(PROJECT)
DB   = p.db                              # <專案根目錄>/<PROJECT>/warehouse.duckdb
LAKE = DB.with_suffix(".ducklake")

def connect(read_only: bool = False, threads: int = 6, mem: str = "11GB"):
    con = duckdb.connect(str(DB), read_only=read_only)
    if not read_only:                                    # 唯讀連線不准改 session 設定
        con.execute(f"SET threads = {threads}")          # ⚠️ 最該先調的參數（W11）
        con.execute(f"SET memory_limit = '{mem}'")       # 約實體記憶體 70%
        con.execute("SET temp_directory = 'E:/duckdb_tmp'")   # 本機 SSD，非網路碟
        con.execute("SET preserve_insertion_order = false")   # 副作用見 W8
    con.execute("INSTALL encodings; LOAD encodings;")    # ⚠️ Big5/CP950 必備（W1）
    con.execute(f"ATTACH IF NOT EXISTS 'ducklake:{LAKE}' AS mart "
                f"(DATA_PATH '{LAKE.parent / 'mart_data'}')")
    return con
```

`threads` 依 RAM 決定，官方 Bestpractice「Aim for 1-4 GB memory per thread」，聚合型 1–2 GB/thread、JOIN 型 3–4 GB/thread（research/01 §9.1）：

| 實體 RAM | 聚合型工作負載 | JOIN 型工作負載 |
|---|---|---|
| 16 GB | `SET threads = 6`（留 4 GB 給 OS/Python） | `SET threads = 3` |
| 32 GB | `SET threads = 12` | `SET threads = 6` |

**唯讀場景一律 `connect(read_only=True)`**：報告生成、儀表板、`verify_outputs.py`。多支腳本可同時唯讀；寫入場景確保同時只有一個行程（W7）。

**更新時的三條紀律：**

1. **不要默默改掉。** 改了任何規則要在文件末尾註明日期與理由，並保留舊寫法作為向後相容的說明——已經照舊規則建好的專案不會自動遷移。
2. **凡是數字都要有出處。** 100 MB 分區門檻、122,880 列 row group、`partitioned_write_max_open_files = 100`、threads 對照表，全部來自 DuckDB 官方文件並在 research/01 標了節次。新增門檻時比照辦理，寫不出出處就不要寫進來。
3. **交叉引用，不要複製。** 這份文件寫「倉儲層該怎麼做」，18 章寫「這個工具會怎麼騙你」。同一件事只在一邊寫完整，另一邊用「見 18-Txx」指過去。兩邊都寫，遲早只改一邊。**這條不只對 18 章成立，對所有 reference 都成立**——尤其 script 的實作骨架，一支 script 的規格只能有一個正本（例如收圖只在 19 §6.2，倉儲維護只在 §6.4）。
