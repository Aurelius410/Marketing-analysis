# 資料模型規格

這份文件是整套 skill 的地基。後面每一份 reference —— 體檢、分群、RFM、購物籃、歸因、實驗 —— 都假設資料已經長成這裡定義的樣子。地基歪了，上面蓋什麼都是斜的，而且**斜得看不出來**：模型會跑、圖會出、報告會完整，只是數字錯了。

漏掉這份文件的後果不是抽象的。少一個 `txn_type` 欄位，一位一年沒買的顧客會因為辦了退貨而被算成「最近極活躍」，進 VIP 名單收禮（見 18-G2）。少一個 `dim_fx_rate`，USD 帳戶的 spend 3,200 會被當成 NT$3,200，ROAS 從真實的 1.18 算成 37.5，然後把 60% 預算移過去。少一張 SCD2 的 `dim_store`，門市改裝換代碼會讓同店銷售從 +3% 算成 −8%，於是停掉一個實際有效的資本支出計畫。這三件事都不會報錯，都不會有紅字，都會安靜地進報告。

四大資料檔的規格來自任立中《大數據行銷 IB5082》第二講（p.31／p.39／p.44–47／p.51–55）；六域擴充與治理域來自 `00_source_archive/research/gap-data-engineering.md` 的 D1–D22 缺口審查；三份實測資料集的欄位事實來自 `local/資料集剖析/marketing_datasets_profile.md` 與 `gdrive/own/03_新資料集剖析_3C與超市.md`。凡是硬規則，後面都附了它為什麼是硬的。

## 一、四大資料檔的原始規格（IB5082 L2）

任老師的架構是**四大資料檔缺一不可**（L2 p.55）。多數人只做客戶檔＋交易檔，於是日期效應與產品屬性偏好這兩整類分析從一開始就不存在——不是做不好，是做不出來。

欄位一字不漏照抄講義原文，右欄是這個欄位服務哪個下游分析（對應 L2 p.13 的「欄位設計 → 下游分析任務」表；**沒有答案的欄位就不要蒐集**）。

### 1.1 客戶基本靜態資料檔（Static Customer Profile，L2 p.31）

| 群組 | 欄位（原文） | 服務的下游分析 |
|---|---|---|
| 識別 | 會員號碼、登記日期 | 全部；`登記日期` 是 tenure/cohort 的唯一來源（18-G3） |
| 聯絡 | 姓名、住址、電話 | DM/EDM 可執行性；PII，須雜湊（18-G13） |
| 人口統計 | 生日、性別 | 卡方那一章、分群後的輪廓描述（**不得當分群輸入**，18-E2） |
| 社經 | 教育程度、職業、職位 | 同上；職業亦是 B2B2C 判斷 |
| 社經 | 年收入、居住型態 | 支付能力代理變數、價格帶決策 |
| 家庭 | 家庭成員、生命週期 | 家庭生命週期分析、品類需求推斷 |
| 心理／行為傾向 | 休閒活動、嗜好 | 訴求文案、內容選題 |
| 溝通偏好 | 資訊收受種類 | **決定挽回動作能不能執行**；缺此欄的名單無法落地 |
| 心理 | 生活型態、人格特質 | 分群外部效度驗證、$f(X)=g(Z)$ 的 $X$ 側 |

| 群組 | 欄位（原文） | 服務的下游分析 |
|---|---|---|
| 交易核心 | 購買日期、金額、數量 | RFM、CAI、CLV、成長分解——**日期必須存到「時」**，否則做不出消費時段分析（p.41 第 3 表） |

| 收款 | 付款方法類別、收款日期 | 付款方式分析、分期行為 |
| 行銷刺激 | 促銷活動內容 | 促銷歸因；缺此欄只能做相關不能談增量（18-G5） |

| 售後 | 滿意度、報怨處理 | 流失預測的領先指標 |

### 1.3 產品特性編碼檔（Product Coding，L2 p.52 / p.54）

| # | 欄位（原文） | 服務的下游分析 |
|---|---|---|
| 1 | 外國知名廠牌 | 品牌構面（Brand）、購物籃、推薦系統 |
| 2 | 本國知名廠牌 | 同上 |
| 3 | 製造來源國 | 規格構面（Design）、產地偏好 |
| 4 | 外觀樣式 | 新品推薦、屬性層偏好學習 |
| 5 | 產品功能 | 同上 |
| 6 | 相對價格 | 價格帶、功能價格比（p.53 範例值 1.58） |
| 7 | 距離產品上架日之期間（p.54 新增） | 嘗新傾向（innovativeness）、新品導入速度 |

### 1.5 三條硬約束（違反即不得往下走）

| # | 約束 | 出處 | 違反的具體後果 |
|---|---|---|---|
| **C1** | **日期維度一天一列、連續不跳號**；交易可為零但日期列必須存在 | L2 p.45（1,026 天無缺日） | 用 `SELECT DISTINCT txn_date FROM fact` 生 `dim_date` → 零銷售日消失 → 迴歸把 0 當缺值 → 週一（多為休館日）平均銷售被高估 → 「週一表現不錯，不需調整」 |
| **C2** | **事實表長格式（一列一筆／一品項）**，禁止存彙總值 | L2 p.26「縱橫交錯」、p.22 Panel Structure | 只存月彙總 → 無法算 interpurchase time → ARFM 的 A 整維消失 → 退化成 RFM（18-術語表） |
| **C3** | **四檔缺一不可** | L2 p.55 | 只有顧客檔＋交易檔 → 日期效應與產品屬性偏好兩類分析永久缺席，且報告不會顯示「缺席」，只會沒有那兩章 |

```sql
-- C1 的機械化斷言（放 sql/checks/dim_date__continuous.sql）
SELECT
    COUNT(*)                                              AS n_rows,
    DATE_DIFF('day', MIN(d_date), MAX(d_date)) + 1        AS n_expected,
    COUNT(*) - (DATE_DIFF('day', MIN(d_date), MAX(d_date)) + 1) AS gap
FROM dim_date
HAVING gap <> 0;   -- 回傳任何列 = error，不准往下走
```

## 二、從四大檔擴充成六域

四大檔覆蓋的是 D1／D2／D3，而且只覆蓋一部分。任老師的架構寫於「行銷資料庫」年代，它預設所有資料都來自自家 POS 與問卷；今天的專案還要接廣告平台、網站、店內感測，而這三者的口徑陷阱（時區、幣別、回填、歸因窗、UTM、bot、同意管理）在四大檔裡完全沒有對應物。**D6 治理域則是四大檔完全沒有的東西**——它記的不是業務，是「我們用什麼口徑量的」。

| 域 | 表 | grain（一列＝什麼） | 對應四大檔 | 缺了會怎樣 |
|---|---|---|---|---|
| **D1 顧客域** | `dim_customer` | 一位顧客的一個有效期間（SCD2） | 靜態檔 | 覆寫式更新 → 搬家的 40 位顧客把兩年前在高屏的消費全歸到大台北 |

| **D2 交易域** | `fact_transaction` | **一列一品項**（發票明細層） | 動態檔 | — |

| **D3 時間域** | `dim_date` | **一天**（連續不跳號） | 日期編碼檔 | 見 C1 |

## 三、完整 DDL（DuckDB 1.5.5）

### 3.1 全域型別與命名規約

| 類別 | 規則 | 理由 |
|---|---|---|
| 金額 | **`DECIMAL(18,4)`，禁止 `DOUBLE`/`FLOAT`** | DOUBLE 累加千萬列產生浮點誤差，與財務對帳永遠差幾元，每次都要花時間確認「是浮點還是漏資料」 |
| 比率 | `DECIMAL(18,8)`，一律存 **ratio（0.0235）** 不存 percent | 廣告平台 CTR 兩種寫法混算 → 「整體 CTR 119%」 |
| 匯率 | `DECIMAL(18,8)` | 同上，且匯率是維度資料不是常數 |
| 自然鍵 | 一律 `VARCHAR` | 前導零、跨源合併、字串黏接碰撞（`89&40526` vs `894&0526` 都是 `8940526`） |
| 代理鍵 | `BIGINT`，命名 `*_key` | SCD2 join 用；事實表只存 `*_key` |
| 表名欄名 | **全小寫 snake_case ASCII，禁止中文** | partition value 出現中文會炸；`smf.ols('刷卡金額 ~ 年齡')` 在 patsy 識別字解析上會出問題。中文顯示名放 `dim_column_label` |
| 稽核欄 | 每張 raw／staging 表必帶 `_source_file`、`_ingested_at` | 重複載入可歸因到具體檔案 |

### 3.2 D1 顧客域

```sql
CREATE TABLE dim_customer (
    customer_key      BIGINT       PRIMARY KEY,  -- 代理鍵，事實表存這個
    person_key        VARCHAR      NOT NULL,     -- map_identity 解析後的「人」
    customer_id       VARCHAR      NOT NULL,     -- 自然鍵＝會員號碼
    registered_date   DATE,                      -- 登記日期（tenure/cohort 唯一來源）
    -- PII：一律雜湊，明碼只留 01_raw 且不進 git（18-G13）
    name_hash         VARCHAR,
    address_hash      VARCHAR,
    phone_hash        VARCHAR,
    zip_code          VARCHAR,                   -- 可分析的地理粒度
    birth_date        DATE,                      -- 存生日，不存年齡（見 §八）
    gender            VARCHAR,                   -- 正規化為 'M'/'F'/'U'
    education         VARCHAR,
    occupation        VARCHAR,
    job_title         VARCHAR,
    annual_income_band VARCHAR,
    housing_type      VARCHAR,
    household_size    INTEGER,
    family_lifecycle  VARCHAR,                   -- 家庭生命週期
    leisure_activity  VARCHAR,
    hobby             VARCHAR,
    contact_pref      VARCHAR,                   -- 資訊收受種類：決定挽回動作能否執行
    lifestyle_segment VARCHAR,
    personality_trait VARCHAR,
    channel_pref      VARCHAR,
    member_tier       VARCHAR,                   -- 會員等級：SCD2 屬性
    -- SCD Type 2
    valid_from        TIMESTAMPTZ  NOT NULL,
    valid_to          TIMESTAMPTZ  NOT NULL DEFAULT TIMESTAMPTZ '9999-12-31 00:00:00+00',
    is_current        BOOLEAN      NOT NULL,
    _source_file      VARCHAR,
    _ingested_at      TIMESTAMPTZ
);

CREATE TABLE map_identity (
    person_key        VARCHAR      NOT NULL,     -- 解析後的人
    id_type           VARCHAR      NOT NULL,     -- customer_id / card_id / anonymous_id / email_hash / device_id
    id_value          VARCHAR      NOT NULL,
    merge_method      VARCHAR      NOT NULL,     -- exact / rule / probabilistic
    confidence        DECIMAL(5,4),              -- probabilistic 必填
    merge_event_id    VARCHAR,                   -- 哪一次合併造成的
    reviewed_by       VARCHAR,                   -- 人工抽驗紀錄（18-G1 要求抽驗，這裡變成欄位）
    valid_from        TIMESTAMPTZ  NOT NULL,     -- identity 有時間維度：縫合會回溯改寫歸因
    valid_to          TIMESTAMPTZ  NOT NULL DEFAULT TIMESTAMPTZ '9999-12-31 00:00:00+00',
    PRIMARY KEY (id_type, id_value, valid_from)
);
```

> `map_identity` 的 `valid_from/valid_to` 不是形式主義。匿名→已知的縫合窗口若開到 180 天，很久以前的匿名行為會被算進來讓上層通路功勞虛胖；完全不縫合則展示廣告的功勞被抹光，「展示廣告零轉換，建議砍掉 NT$180,000/月」。**縫合回溯窗口建議 30 天，並寫進指標字典。**

### 3.3 D2 交易域

```sql

    txn_line_id       BIGINT       PRIMARY KEY,  -- 代理鍵。3C 有 186 筆、超市有 364 筆全欄重複
                                                 -- 且是真實資料（同單掃了 12 條同款省電燈泡），
                                                 -- 所以沒有自然主鍵，必須加 row_id，禁止 drop_duplicates()
    txn_id            VARCHAR      NOT NULL,     -- 單頭鍵＝籃（basket）。購物籃分析用它
    line_no           INTEGER,
    customer_key      BIGINT       NOT NULL,
    person_key        VARCHAR      NOT NULL,
    card_key          BIGINT,                    -- 卡／裝置只能是通路維度，不得當分析主體
    product_key       BIGINT,
    store_key         BIGINT,
    campaign_key      BIGINT,                    -- 促銷活動內容（L2 p.39）→ 接 D4
    -- 三個時間欄，見 §四
    event_ts_utc      TIMESTAMPTZ  NOT NULL,
    event_ts_local    TIMESTAMP    NOT NULL,
    biz_date          DATE         NOT NULL,     -- 唯一允許 join dim_date 的欄
    -- 交易類型，見 §五
    txn_type          VARCHAR      NOT NULL,     -- sale/return/void/exchange_out/exchange_in
    original_txn_id   VARCHAR,                   -- return/exchange 必填
    quantity          DECIMAL(18,4) NOT NULL,
    unit_price        DECIMAL(18,4),
    line_amount_gross DECIMAL(18,4) NOT NULL,    -- 該列小計，已含數量，不可再乘 quantity
    discount_amount   DECIMAL(18,4) DEFAULT 0,
    line_amount_net   DECIMAL(18,4) NOT NULL,
    currency          VARCHAR      NOT NULL,
    amount_twd        DECIMAL(18,4) NOT NULL,
    fx_rate_date      DATE,
    payment_method    VARCHAR,                   -- 現金/信用卡/支票/提貨單/禮券/應收
    is_installment    BOOLEAN,                   -- 一般消費 / 分期消費
    purchase_reason   VARCHAR,                   -- 汰舊換新/舊機損壞/新添購/送人（L2 p.40 紅框）
    purchase_plan     VARCHAR,                   -- 計畫型 / 非計畫型 → slack vs emergency purchase
    info_source       VARCHAR,                   -- 親友/DM/報紙/雜誌/店面佈置/網路/電台（L2 p.40 紅框）
    satisfaction_score DECIMAL(5,2),
    complaint_flag    BOOLEAN,
    is_test_txn       BOOLEAN      DEFAULT FALSE,-- 標記不刪，移 _quarantine 並記日誌
    data_as_of_date   DATE         NOT NULL,     -- 退貨記回原交易日 → 歷史會變動，見 §五
    _source_file      VARCHAR,
```

## 四、三個時間欄的硬規則

事實表一律存三個時間欄，一個都不能省，而且**用途互斥**。省掉的代價：做「線上瀏覽 → 門市購買」的同日轉換分析，web 用 GA4 的 UTC 日切、POS 用本地日切，台灣時間 00:00–08:00 的網站行為會被歸到前一天。這段流量只佔 6%，但它讓「週日線上導流」虛高 6 個百分點 → 把 EDM 從週三改到週日 → 成效下降，而且沒有人會想到是時區。

| 欄位 | 型別 | 唯一用途 | 禁止用途 |
|---|---|---|---|
| `event_ts_utc` | `TIMESTAMPTZ` | **唯一可跨源比較的時間**；SCD2 的 as-of join 用它 | 不要拿去 `CAST(... AS DATE)` 當業務日 |
| `event_ts_local` | `TIMESTAMP` | 呈現用（報表上顯示給人看的時間） | **禁止用於跨源比較**（不同來源的 local 不是同一個時區） |
| `biz_date` | `DATE` | **唯一允許 join `dim_date` 的欄**；所有日粒度彙總 | 不要用它做小時級分析 |

$$\texttt{biz\_date} = \operatorname{CAST}\Big(\big(\texttt{event\_ts\_utc} \text{ AT TIME ZONE 'Asia/Taipei'}\big) - \texttt{INTERVAL } h \texttt{ HOUR} \ \text{ AS DATE}\Big),\quad h = \texttt{biz\_day\_cutoff\_hour}$$

跨夜業態（餐飲、娛樂、便利商店，打烊 02:00–06:00）令 $h=6$；一般零售 $h=0$。$h$ 存在 `dim_store.biz_day_cutoff_hour`，**不是寫死在 SQL 裡**——同一家公司不同店型的 $h$ 可以不同。

$h=0$ 時會發生什麼：週五 23:00–02:00 的營收被拆到週五與週六兩天，其中深夜段（常佔該營業日 35%）記到週六 → 「週六是最強日」→ 人力排班與促銷檔期押在週六白天，實際尖峰是週五深夜。更糟的是那筆營收會 join 到「週六、週休二日=1」的 `dim_date` 列，而行為實際發生在「週五、平日」的情境，**日期效應迴歸的係數整體被污染**。

```
時間欄怎麼選（決策樹）
│
├─ 要跟另一個來源的時間比大小 / 排序 / 算間隔？
│    └─ YES → event_ts_utc（唯一正解）
│
├─ 要 join dim_date、要 GROUP BY「日」、要算 R/F/CAI？
│    └─ YES → biz_date（唯一正解；join 其他欄一律視為 bug）
│
├─ 要在報表／圖表上顯示一個時間給人看？
│    └─ YES → event_ts_local
│
└─ 要做小時級分析（時段、尖峰）？
     └─ 用 event_ts_local 取小時，但必須先確認該來源的 source_tz 已宣告
```

```sql
-- raw 層時間一律存 VARCHAR 原樣 + 強制附 source_tz（來自契約檔，不是猜的）
-- staging 的標準轉換：
CREATE OR REPLACE TABLE stg_pos_txn AS
SELECT
    r.*,
    (r.txn_ts_raw::TIMESTAMP AT TIME ZONE c.source_tz)              AS event_ts_utc,
    (r.txn_ts_raw::TIMESTAMP AT TIME ZONE c.source_tz
        AT TIME ZONE 'Asia/Taipei')                                 AS event_ts_local,
    CAST((r.txn_ts_raw::TIMESTAMP AT TIME ZONE c.source_tz
        AT TIME ZONE 'Asia/Taipei')
        - INTERVAL (s.biz_day_cutoff_hour) HOUR AS DATE)            AS biz_date
FROM raw_pos_txn r
JOIN source_contract c ON c.source = 'pos'
JOIN dim_store       s ON s.store_id = r.store_id AND s.is_current;

-- 檢查：任何 TIMESTAMP 欄若無對應的 source_tz 宣告 → 不准進 staging（error）
-- 檢查：各來源的「小時分布」若出現整體位移 8 小時的形狀（POS 尖峰落在凌晨 4–6 點）→ error
```

## 五、交易類型與退貨

`txn_type` 與 `original_txn_id` **兩欄必填**。沒有這兩欄的資料源，在 M1 資料體檢就要標「**無法正確計算 R/F**」，不是「先做做看」。

| `txn_type` | 語意 | `original_txn_id` | 進 R 的計算？ | 進 F？ | 進 M（淨額）？ |
|---|---|---|:--:|:--:|:--:|
| `sale` | 正常銷售 | NULL | **是** | **是** | 加 |
| `return` | 退貨 | **必填** | 否 | 否 | 減 |
| `void` | 當日作廢／沖銷 | **必填** | 否 | 否 | 抵銷（原列一併排除） |
| `exchange_out` | 換貨的退出腳 | **必填** | 否 | 否（與 in 淨計 0 次） | 減原價 |
| `exchange_in` | 換貨的換入腳 | **必填** | 否 | 否 | 加新價 |

$$M_i^{\text{net}} = \sum_{t:\ \texttt{sale}} a_t \;-\; \sum_{t:\ \texttt{return}} |a_t| \;+\; \Big(\sum_{t:\ \texttt{exchange\_in}} a_t - \sum_{t:\ \texttt{exchange\_out}} |a_t|\Big)$$

**R 與 F 的計算必須 `WHERE txn_type = 'sale'`**，這是硬規則不是建議。漏掉的具體情境（呼應 18-G2「退貨與取消未處理」，完整推導見 `00_source_archive/research/gap-data-engineering.md` D8）：一位顧客最後一次購買是 2025-08-10，2026-07-20 辦了退貨；退貨在系統裡是一筆交易列，`R = 基準日 − MAX(txn_date)` 得到 **6 天** → 這位一年沒買的顧客被算成「最近極活躍」→ 落進 `R_score=5` → 進「冠軍客戶」名單 → 收到 VIP 禮與加購推薦。F 則被換貨（一退一買）重複計算：3% 訂單換貨的服飾品類，顧客 F 各多算 2 次而不是 0 次 → 「服飾客群忠誠度最高」→ 把 CRM 預算移到一個由退換貨造成的假象。

**這組 bug 在課程資料集上 100% 測不出來**——信用卡檔實測「負值 0、零值 0、不含退貨」。所以它必須由 `tests/fixtures/dirty_mini.parquet` 的髒資料驗證，而不是靠綠燈。

**期間錯配與 restatement 政策**：12 月營收 1,000 萬，其中 80 萬在隔年 1 月退貨。記在退貨日 → 12 月虛高 8%、1 月被打成 −8%，「1 月營收衰退」是假的；記在原交易日 → 已公布的 12 月報表事後被改寫，而沒有人知道被改寫過。**兩種都對，但必須選一個、宣告它、並讓改寫可被偵測**。本 skill 的預設：**M 用淨額且記在原交易日**，靠 `data_as_of_date` 讓改寫可偵測，並在 `dim_metric_definition.restatement_policy` 明寫。

```sql
-- 標準 RFM 來源視圖：兩個 WHERE 都不可省（與 references/17 §二一致）
CREATE OR REPLACE VIEW v_txn_for_rfm AS
SELECT * FROM fact_transaction
WHERE txn_type = 'sale'          -- 不省它：退貨列污染 R，且完全沉默
  AND biz_date <= DATE '2012-12-01';  -- 不省它：目標洩漏（18-G4）

-- 毛額／退貨／淨額三欄對照（18-G2 只要求兩欄，這裡要三欄）
SELECT
    person_key,
    SUM(CASE WHEN txn_type='sale' THEN amount_twd ELSE 0 END)              AS m_gross_twd,
    SUM(CASE WHEN txn_type IN ('return','exchange_out') THEN amount_twd ELSE 0 END) AS m_return_twd,
    SUM(CASE WHEN txn_type IN ('sale','return','exchange_in','exchange_out')
             THEN amount_twd ELSE 0 END)                                   AS m_net_twd
FROM fact_transaction
WHERE biz_date <= DATE '2012-12-01'
GROUP BY person_key;
```

## 六、SCD Type 2

預設的維度更新是覆寫，而覆寫等於**用今天的維度值改寫歷史**。判準只有一句話：

> **這個屬性有沒有被用在「分組比較歷史數字」上？有就 SCD2，沒有就 Type 1。**

```
某個維度屬性要不要 SCD2？
│
├─ 這個屬性會變嗎？
│   ├─ 不會（生日、註冊日、性別、原始建檔通路）→ Type 1（直接覆寫）
│   └─ 會 ↓
│
├─ 它會被拿去 GROUP BY 然後比較跨期數字嗎？
│   ├─ 不會（只是聯絡資訊、備註）→ Type 1
│   └─ 會 ↓
│
├─ 它的變動與「被比較的數字」有因果關係嗎？
│   ├─ 有（卡等是消費高之後才升的）→ SCD2，而且分析時要用交易當下的值
│   └─ 沒有（純粹外生的搬家）→ SCD2（否則歷史被搬到新地區）
│
└─ 自然鍵本身會變嗎？（門市換代碼、卡片補發、SKU 換碼）
    └─ 會 → SCD2 + 另建 *_group_id 串接
```

| 表 | SCD2 屬性 | Type 1 屬性 | 為什麼 |
|---|---|---|---|

**`dim_store.store_group_id` 是全表最重要的一欄。** 門市改裝重開代碼從 `T012` 換成 `T105`（POS 系統常態）→ 直接 `GROUP BY store_id` 算同店銷售 → `T012` 在 6 月「關店」、`T105` 在 7 月「新開」→ SSS 把 `T105` 當新店排除、把 `T012` 當關店排除 → 該商圈 SSS 從真實的 **+3%** 算成 **−8%** → 「改裝沒有帶來成長，建議暫停後續五家門市的改裝計畫」→ 停掉一個實際有效的資本支出計畫。搬遷、換代碼、加盟轉直營一律用同一個 `store_group_id` 串起來。

```sql
-- 事實表存代理鍵，join 用 as-of（DuckDB 原生支援 ASOF JOIN，寫起來不痛）
SELECT f.biz_date, c.member_tier, SUM(f.amount_twd) AS amount_twd
FROM fact_transaction f
ASOF JOIN dim_customer c
       ON c.person_key = f.person_key
      AND c.valid_from <= f.event_ts_utc     -- 取交易當下有效的那一版
WHERE f.txn_type = 'sale'
GROUP BY 1, 2;

-- 同店銷售（SSS）硬規則：GROUP BY store_group_id，且限兩期都營業的店
WITH both_periods AS (
    SELECT s.store_group_id
    FROM fact_transaction f JOIN dim_store s ON s.store_key = f.store_key
    GROUP BY 1
    HAVING COUNT(DISTINCT CASE WHEN f.biz_date BETWEEN DATE '2011-01-01' AND DATE '2011-12-31'
                               THEN f.biz_date END) > 0
       AND COUNT(DISTINCT CASE WHEN f.biz_date BETWEEN DATE '2012-01-01' AND DATE '2012-12-31'
                               THEN f.biz_date END) > 0
)
SELECT ... FROM ... WHERE s.store_group_id IN (SELECT store_group_id FROM both_periods);
-- 報表必須標明：納入 N 家、排除 M 家及排除原因

-- SCD2 的三個必查 bug（sql/checks/dim_scd2__no_overlap.sql）
--   1) 同一自然鍵的有效期間不得重疊
--   2) 不得有空隙
--   3) is_current 恰好一列
```

## 七、分域啟用（degraded mode）

現實裡幾乎不會六域齊全。**缺域不是延後分析的理由，是限制結論範圍的理由**——但範圍必須在報告裡明寫，不能靠讀者自己推。這對應六條紀律的第六條「降級不留空」。

| 手上有的域 | 可以做 | **明確不可做** | 報告必須明寫的句子 |
|---|---|---|---|
| 只有 **D2**（交易，無顧客檔） | 品類貢獻、ABC、購物籃（若明細粒度）、時序趨勢 | 一切顧客層分析：RFM／CAI／CLV／分群／流失 | 「本分析無法回答**任何顧客層問題**（誰值錢、誰要跑），因為交易無法歸戶。」 |
| **D1+D2**（無日期維度） | RFM、CLV、分群、購物籃 | 日期效應、檔期效益、季節性拆解、「不購買」機率 | 「本分析無法回答**節慶／星期／天氣**類問題；零銷售日不存在於資料中，趨勢圖的低點可能是缺日不是衰退。」 |
| **D1+D2+D3**（四大檔齊，多數專案的起點） | RFM／ARFM／CAI／CRI／CLV、分群、遷徙、購物籃、因素分析、成長分解、日期效應 | ROI／ROAS／CAC／歸因／預算配置／增量 | 「本分析**無法歸因至行銷投入**（18-G5）。所有『某活動有效』的敘述均為相關，證據等級為『相關』。」 |
| **＋D4**（行銷投入） | ROAS、CAC、通路效率、促銷拆解、MMM（大樣本） | 因果宣稱、跨平台 conversions 相加、增量估計 | 「平台自報 conversions **僅各自呈現不予加總**（各平台歸因窗不同）；跨平台總量以內部訂單為單一真相。無對照組，故不談增量。」 |
| **＋D5**（行為） | 漏斗、路徑、線上到線下、進店率／提袋率、上層通路貢獻 | 用 GA4 session 當母體算滲透率／市占 | 「網站指標僅代表**可量測樣本**（量測涵蓋率 X%）；session 採自訂定義 v1，與 GA4 介面數字不可直接比較。」 |
| **＋D6**（治理） | 跨期比較、多幣別彙總、可重現交付、口徑追溯 | —（此時才算完整） | 「本報告數字綁定 `run_id` / snapshot / 指標字典版本，可重跑重現。」 |
| **缺 D6 但有其他全部** | 單期分析 | 跨期比較、多幣別彙總、宣稱可重現 | 「本報告的數字**無法保證重跑一致**（無 snapshot 綁定），跨期比較未經口徑版本控制。」 |

## 九、維護條款

這份文件是地基，所以**改它的成本最高、也最需要留痕**。

**什麼情況要更新：**

1. **接了新的資料型態**（例如 App 事件、客服工單、評論文本）→ 要判斷它屬於哪一域、要不要新增表，新增後回頭更新 §二的域表與 §七的降級表。文本資料進來時建 `fact_review` 並接進 D1（18-G16）。
2. **某個欄位第一次被用來分組比較歷史數字** → 它就從 Type 1 升級成 SCD2，要在 §六 的表裡加一列並註明升級日期與觸發的分析。
3. **新增了平台或幣別** → `dim_attribution_setting`、`dim_fx_rate` 要補列；§三 的 DDL 若因此加欄，同步更新契約檔。
4. **`references/17_指標公式庫` 的口徑改了** → 檢查 §五的 `v_txn_for_rfm` 與 §八的注意事項是否還一致。兩份文件的 `txn_type='sale'` 過濾必須同步，不同步就是靜默錯誤。
5. **實測資料集換了或新增了** → §八要加一欄，並重新確認「三份都算得出」那張表是否還成立。

**更新時要注意：**

- **DDL 改欄位一律 append-only**，舊欄位標 `deprecated_since` 而不是刪掉。刪欄會讓舊的 `run_id` 無法重跑，直接違反可重現承諾。
- **改型別要先問「有沒有已交付的報告引用過這張表」**。改了就要在 `log_measurement_change` 記一列，並在下一份報告的異動清單裡寫明。
- **凡是本文寫「硬規則」的地方，放寬前要先找到一個具體的失效案例**，並把該案例寫進本文——與 18 的紀律相同：這份文件的權威來自每一條都可追溯。
- **不要默默改**。改了口徑而沒有異動清單，等於製造一個沒有人知道的斷層。
