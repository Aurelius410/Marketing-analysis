# 資料體檢（M1）

M1 是整條產線的第一個硬卡點，也是唯一一個「錯了之後下游全部白做」的模組。M2 檢定前提、M3 轉換、M6 分群、M8 算 RFM/CAI，全部建立在「這批資料的粒度是什麼、主鍵是誰、哪些值是假的」這三個判斷上。這三個判斷在 M1 做，而且只在 M1 做一次。

漏掉體檢的代價不是「報告不夠嚴謹」，是**產出一份每個數字都算對、但每個數字都在回答錯誤問題的報告**。最貴的實例就在包子自己的檔案裡：課程資料集的 `int` 欄含 100 個 `9999` 哨兵，不排除直接算平均購買間隔得 **199.46 天**，真值是 **10.79 天**，差 **18.5 倍**。若用 199.46 反推流失門檻，會把「超過 200 天未購買」訂成流失定義 —— 100 位客戶裡只有 3 位被標流失，而 RFM 實算的「沉睡/流失」群有 **28 位**，漏掉的 25 人合計 M 為 **NT$947,152**，占總營收 **6.4%**（出處：`local/資料集剖析/marketing_datasets_profile.md` §2.6、§2.7）。這種錯誤不會報錯、不會有紅字、pipeline 一路綠燈跑到底。

M1 走完必須停下來等包子回覆。回報四段：做了什麼 → 發現什麼 → 因此建議什麼 → 需要你決定什麼。**「因此建議做哪些分析、不做哪些分析」是 M1 的主產出，不是附註。**

## 一、體檢的執行順序

七步，順序不可交換。每一步的失敗都會讓後面那步的結論失效 —— 例如還沒判定粒度就開始逐欄剖析，你算出來的「缺失率」分母是錯的（訂單明細層的 42 萬列 vs 顧客層的 8.6 萬人，同一欄的缺失率完全不同）。

```
① 檔案盤點        ── 有哪些檔、多大、真的是它宣稱的格式嗎、能不能整份載入
       │
       ▼
② schema 契約比對  ── contracts/<source>.yml vs 實檔；欄位改名 / 新增 / 消失
       │              ⛔ 契約有、實檔沒有 → error｜實檔有、契約沒有 → error
       ▼
③ 逐欄剖析        ── 型別、缺失、唯一值、五數摘要、形狀量數、類別分布、日期範圍
       │
       ▼
④ 粒度與主鍵判定   ── 一列代表什麼？主鍵候選？重複列多少？→ 寫進契約並轉成持續斷言
       │
       ▼
⑤ 品質檢查三桶     ── error / warning / info + exit code；error 直接擋住不准往下
       │
       ▼
⑥ 六域缺口盤點     ── D1–D6 哪些域有資料、哪些沒有
       │
       ▼
⑦ 分析可行性判定   ── ✅ 做什麼｜❌ 不做什麼｜⚠ 可做但要標警語   ← M1 的主產出
```

| 步 | 輸入 | 產出 | 失敗時怎麼辦 |
|:--:|---|---|---|
| ① | 原始檔路徑 | `開案與問題定義/檔案盤點.md` | magic bytes 與副檔名不符 → 以 magic bytes 為準，記一則 warning |
| ② | 契約 + 原始檔（**契約檔欄位規格見 `02_資料模型規格.md` §十**）| `check_schema_contract.py` 報告 | 首次進場無契約 → 由 ③ 的剖析結果**生成**契約草稿，交包子確認後才算數 |
| ③ | 原始檔 | `開案與問題定義/欄位總表.csv` + 圖 | 檔案大到不能整份載入 → 走串流剖析（見下方程式碼） |
| ④ | ③ 的結果 | 契約的 `grain:` 欄位 + `checks/<table>__grain_unique.sql` | 找不到唯一鍵 → 明寫「本表無主鍵」，並列出最接近的複合鍵與重複率 |
| ⑤ | ③④ + 契約 | `check_data_quality.py` 三桶清單 | error 桶非空 → **停在這裡**，不准進 M2 |
| ⑥ | ⑤ 通過的資料 | 六域缺口表（§六） | — |
| ⑦ | ⑥ + M0 的假說登錄表 | 「建議做／不做」清單 | 假說全部落在缺失的域 → 回 M0 重談問題 |

**檔案盤點的三個必查項**，全部有實測依據：

| 查什麼 | 怎麼查 | 實測案例 |
|---|---|---|
| 副檔名詐騙 | 讀前 200 bytes 的 magic bytes；`504b 0304` + `[Content_Types].xml` = 真 OOXML | `credit_card_transactions (1).csv.xlsx` 227 MB，經查是**貨真價實的 xlsx 不是改名的 csv**，必須走 openpyxl 串流（profile §1.4）|
| 能不能整份載入 | 看 zip 成員的 `uncompressed` 大小，不是看檔案大小 | 同上檔案：`sheet1.xml` 解壓後 **971 MB** + `sharedStrings.xml` **50 MB**，`pandas.read_excel()` 峰值可破 8–10 GB（profile §1.4 評註）|
| 上游是不是已經被截斷 | 列數是否恰好 = 1,048,575 或 1,048,576 | 同上檔案列數 **1,048,575**，原始 Kaggle 檔 **1,296,675** 列 → **被 Excel 列上限截斷，遺失約 248,100 列**（profile §0）|

```python
# scripts/profile_dataset.py 的執行骨架（M1 步驟 ①–④）
# 主環境 Python 3.14.1 / pandas 2.3.3 / openpyxl 3.1.5 / duckdb 1.5.5
from pathlib import Path

def run_m1(src_paths: list[Path], contract_dir: Path, out_dir: Path) -> dict:
    inv    = inventory(src_paths)              # ① magic bytes / 解壓後大小 / 列數上限檢查
    schema = check_schema_contract(inv, contract_dir)   # ② 有契約才比對，沒有就生草稿
    if schema.has_error:
        raise SystemExit(1)                    # 契約不符直接擋住，不浪費時間剖析（退出碼語意見 §四）
    cols   = profile_columns(inv)              # ③ 逐欄剖析（規格見 §二）
    grain  = infer_grain(inv, cols)            # ④ 粒度與主鍵（決策樹見 §三）
    emit_contract_draft(contract_dir, cols, grain)
    return {"inventory": inv, "columns": cols, "grain": grain}

# 大檔一律串流，不用 pandas.read_excel
def stream_xlsx(path: Path, sheet: str):
    import openpyxl
    wb = openpyxl.load_workbook(path, read_only=True, data_only=True)
    yield from wb[sheet].iter_rows(values_only=True)
```

## 二、逐欄要產出什麼

每一欄都要跑完下表，**不准挑欄位跑**。理由：你以為沒用的欄常常就是那個炸掉的欄 —— `Unnamed: 10` 看起來是垃圾，實際上它是課程 Step 5 那份「99 位客戶」的 CAI 名單（依 §七 的門檻其中兩位其實不該算，見 Q15），缺失率恰好 1.00%（profile §2.3）。

| 產出 | 適用型別 | 內容 | 判定門檻與出處 |
|---|:--:|---|---|
| 推定型別 | 全部 | `int64` / `float64` / `datetime64[ns]` / `object` / `bool`；**同時記錄 raw 層的原始字串型別** | raw 一律存 VARCHAR，型別轉換延到 staging（research/01 §6）|
| 缺失率 | 全部 | 非空數 / 總列數 | ≥5% warning｜≥40% error（需宣告處理方式）｜≥80% 建議棄用。**【本 skill 訂】** 理由不是統計學，是補值方法的可用性：缺失率 >40–50% 時 MICE/迴歸補值補出來的是模型，不是資料 |
| 唯一值數 | 全部 | `nunique()` 與 `nunique/n` 比值 | 見下方「疑似 ID 欄」判定 |
| 五數摘要 | 數值 | min / q25 / median / q75 / max，外加 mean、std、p95、p99 | p95/p99 用來對照 boxplot 的 1.5 IQR 是否過度標記離群 |
| 形狀量數 | 數值 | 偏度 $g_1$、峰度 $g_2$（excess）、變異係數 CV | 偏度 \|$g_1$\| >1 → 標記「M3 需轉換」（門檻與 SKILL.md 的 M4 驗收門檻一致）｜CV >1 → 分布極度分散，等寬分箱必失效 |
| 類別 top-10 與占比 | 類別 | 前 10 個值 + 各自筆數 + 占比 + 尾部合併占比 | 單一值占比 >95% → 近乎常數欄，標記 info「模型中無資訊量」 |
| 日期 min/max | 日期 | 最早 / 最晚 / 相異日數 / 缺日數 | 相異日數 < 期間天數 → 有缺日，接 §四 的完整度檢查 |
| 疑似 ID 欄 | 全部 | 標記 `suspected_id` | 見下方判定規則 |
| 疑似 helper 欄 | 全部 | 標記 `helper_column` | 欄名符合 `^Unnamed: \d+$` 或全空/近全空 |

**形狀量數的公式**（用 `scipy.stats.skew(bias=False)` / `kurtosis(bias=False)`，與 R 的 `fBasics` 同一族，教材 EDA 標準動作序列第 6 步，出處 `notion/商管統計資料分析/01_eda_regression_anova.md` §1.2）：

$$
g_1 \;=\; \frac{n}{(n-1)(n-2)}\sum_{i=1}^{n}\left(\frac{x_i-\bar{x}}{s}\right)^{3}
$$

$$
g_2 \;=\; \frac{n(n+1)}{(n-1)(n-2)(n-3)}\sum_{i=1}^{n}\left(\frac{x_i-\bar{x}}{s}\right)^{4}\;-\;\frac{3(n-1)^{2}}{(n-2)(n-3)}
$$

$$
\mathrm{CV} \;=\; \frac{s}{\bar{x}} \qquad \text{（僅在全欄為正、且為比例尺度時才有意義；含負值或含 0 一律不報 CV）}
$$

**疑似 ID 欄的判定規則**（三條全中才標，避免把「顧客年齡」這種高基數數值欄誤判）：

```
唯一值比 nunique/n ≥ 0.95
        └─ 且 型別為整數或字串
                └─ 且 （欄名含 id/ID/編號/序號/代碼  或  數值近似連續整數序列）
                        └─ 標記 suspected_id  →  進 §三 的主鍵候選池
                        
反例（不可標）：課程資料集的「生日」欄 100/100 唯一但語意是日期，不是 ID
```

**欄位總表必須有「實務用途」欄** —— 這是包子的招牌欄位，也是把「資料剖析」接上「決策驅動欄位」紀律的唯一接點。用途只能填下列七種之一，填不出來代表這欄還沒被想清楚：

| 用途標籤 | 意義 | 下游約束 |
|---|---|---|
| `subject_key` | 分析主體鍵 | 顧客單位一律 `customer_id`。`card_id` / `device_id` **不得**當分析主體（實測：交易檔的 `信用卡ID` 相異值 130 vs `客戶ID` 100，用錯會得到 130 個假顧客）|
| `fk` | 外鍵 | 進場必查孤兒率 |
| `time_axis` | 時間軸 | 只有標這個的欄可以拿去切 `as_of_date`（見 18-G4）|
| `measure` | 度量 | 要宣告單位與幣別；比率欄要宣告 `ratio` 或 `percent` |
| `segment_input` | 分群輸入（白名單） | **只能是行為指標**：R/F/M/RFM Score/CAI/CRI/因素分數/LN_F/LN_M（見 18-E2）|
| `profile_only` | 剖面變數 | 人口統計變數只能出現在卡方那一章，**不准進分群**（見 18-E2）|
| `helper` / `deprecated` | 輔助欄／棄用 | 不進 staging，但要保留紀錄 |

## 三、粒度與主鍵判定

粒度講的是**一列代表什麼**。這句話寫不出來就不准往下走。課程資料集是最好的反例教材：同一個活頁簿有 11 個工作表、**五種不同粒度**（客戶級 / 卡片級 / 交易級 / 中間計算級 / 彙總級），把 `Step 4` 的樞紐表當成顧客檔讀進來，就會多出一位叫 `Grand Total` 的「顧客」，而且它的 `Sum of Weight = 306,520`（全體加總），會直接衝上任何排行榜第一名（profile §2.6）。

```
粒度判定決策樹

一列代表什麼？先用一句話寫出來 ──→ 寫不出來？回去看原始檔的前 20 列，不要猜
        │
        ▼
單欄唯一？  ── 有 nunique == n 且非空的欄 ──→ 主鍵 = 該欄
        │                                      （多個候選時取語意最像鍵的，其餘標 alt_key）
        └─ 沒有
              │
              ▼
        複合鍵唯一？ ── 試 (subject_key, time_axis)、(subject_key, time_axis, line_no)
              │            (subject_key, fk)、(platform, account, campaign, report_date)
              ├─ 唯一 ──→ 主鍵 = 該複合鍵
              └─ 仍不唯一
                    │
                    ▼
              整列完全重複？
                    ├─ 是 ──→ 真重複，去重並記入清理日誌（判定規則見下）
                    └─ 否 ──→ 粒度比你以為的更細，往下找一層
                              （常見：以為是「一筆交易」，其實是「一筆交易的一個品項」）
```

**重複的判定規則（實測校準過，不要放寬）**：只有「**所有欄位皆同**」才算真重複。課程資料集的 `同卡 + 同日 + 同金額` 出現 **323** 組，但 `交易序號` 全異、產業分類與地點可能不同 —— 這是「同一天在同一家店刷了兩次一樣金額」的正常行為（公用事業自動扣繳、中信錢加值每次 500 元），**整列重複實際為 0**（profile §2.5.5）。用「同卡同日同金額」去重會誤刪 323 組真實交易。

**grain 必須變成持續斷言，不能只是一次性觀察。** M1 的粒度判定是人工判斷，判完之後如果沒有東西守著它，下一批資料進來時它會靜默失效 —— 上游改了分頁邏輯、廣告 API 重複回傳、POS 重跑一次，主鍵就不唯一了，而沒有任何人會發現（出處：`research/gap-data-engineering.md` D13 第 5 點）。

```sql
-- checks/<table>__grain_unique.sql
-- 每次載入都跑，不是只在 M1 跑一次。回傳非 0 列即 error。
-- <grain_cols> 從 contracts/<source>.yml 的 grain: 欄位讀出來，不准寫死在這裡
SELECT <grain_cols>, count(*) AS n_dup
FROM   <table>
GROUP  BY <grain_cols>
HAVING count(*) > 1
ORDER  BY n_dup DESC
LIMIT  20;

-- 參照完整性（同一批跑，孤兒率 >1% error、>0 warning）
SELECT 'tx->customers' AS edge,
       count(*) FILTER (WHERE c.客戶ID IS NULL) AS orphans,
       count(*)                                 AS total,
       count(*) FILTER (WHERE c.客戶ID IS NULL) * 1.0 / count(*) AS orphan_rate
FROM   transactions t LEFT JOIN customers c USING (客戶ID);
-- 課程資料集實測：三個方向（tx→cards、tx→customers、cards→customers）孤兒全部為 0。
-- 這是教學資料的特徵，真實資料通常 1–5%（profile §2.5.5）。
-- 因此這條檢查在課程資料集上永遠綠燈，見 18 章對「乾淨基準集給假安全感」的同一個警告。
```

## 四、品質檢查三桶（error / warning / info + exit code）

三桶的設計來自 18-G11（「缺資料品質關卡 → `check_data_quality.py` 三桶 + exit code，error 直接擋住」）。這一節是把 G11 展開成可執行的條目清單。

**分桶原則**：會**靜默污染平均數或改變分群結果**的放 error，會讓結論不穩但看得出來的放 warning，只是提醒的放 info。哨兵值放 error 不放 warning，理由很現實 —— warning 會被忽略，而它會讓平均間隔差 18.5 倍。

**退出碼語意全 skill 統一**，以 `scripts/setup_check.py`（唯一有實作的 gate）為準：**1 = 有 error 擋住、2 = 只有 warning 可往下**。`20_交付物產製.md` 的 `verify_outputs`、`CLAUDE.md` 的開工檢查都是同一套。**不准在任何腳本裡把 1 和 2 對調** —— 一個照 `if [ $? -eq 2 ]; then 繼續; fi` 寫的 CI wrapper 會在對調後把「有 error 必須擋住」讀成「只是 warning」，在 M1 這個硬卡點 fail open。（`19_圖表與統計表規格.md` §二 配色檢查 `check()` 的退出碼是**分類碼**——1 對比不足／2 CVD 撞色／3 明度非單調——不是嚴重度階梯，不適用本條。）

| exit code | 意義 | 下游行為 |
|:--:|---|---|
| `0` | 三桶皆空，或只有 info | 可進 M2 |
| `1` | **有 error** | **擋住。不准進 M2。** 必須在 `contracts/<source>.yml` 明確宣告處理方式後重跑（契約檔規格見 `02_資料模型規格.md` §十）|
| `2` | 有 warning，無 error | 可進 M2，但 warning 條目必須進報告的「資料限制」節 |
| `3` | 檢查腳本本身失敗 | 修腳本，不准手動略過 |

### 4.1 error 桶（擋住不准往下）

| # | 檢查 | 觸發條件 | 具體會怎麼錯（帶數字） |
|:--:|---|---|---|
| Q1 | **型別 cast 靜默失敗** | cast 後的 NULL 數 ≠ cast 前的空字串/NULL 數 | POS 匯出金額含千分位與 `NT$1,234`，`TRY_CAST` 全部回 NULL 不報錯。若只有 3% 的列（大額交易才有千分位）失敗，該店營收少 18%，落在「表現不佳」而非「明顯異常」的區間 → 排名墊底 → 「建議評估收店」（gap D17）|

### 4.3 info 桶（記錄，不阻擋）

近乎常數欄（單一值占比 >95%）、高基數類別欄（nunique >50 且非 ID）、完全空白欄、規格與實測不符（**【實測】** 講義說 7,771 筆交易，三種方式交叉確認實為 **7,764** 筆 —— 撰寫報告時以 7,764 為準並註記差異，見 18-E22 的樣本數交代規則）。

import sys

BUCKETS = {"error": [], "warning": [], "info": []}

def gate() -> int:
    if BUCKETS["error"]:

        return 2
    return 0

if __name__ == "__main__":

## 六、六域缺口盤點與分析可行性判定

六域星狀模型的定義在 `02_資料模型規格.md`。M1 只做一件事：**盤點哪些域有資料，然後把「缺這個域 → 這些分析要被排除」寫成明確清單**。這張表直接餵給硬卡點回報 —— 它就是「因此建議做哪些分析、不做哪些分析」的骨架。

硬規則（來自框架藍圖 §3.2）：**缺少某一域時，報告必須明寫「本分析無法回答 X 類問題」，而不是用手邊有的資料硬答。**

| 域 | 核心表 | 缺了它 → **明確不可做**（要在報告寫出這句話） | 缺了它 → 可降級做什麼 |
|---|---|---|---|
| **D1 顧客域** `dim_customer` / `map_identity` | 顧客主檔、身分解析 | 顧客分群、CLV、輪廓檢定、任何「顧客層」結論 | 只能做交易層與商品層分析（品類結構、時段結構）|
| 　└ 缺 `map_identity` | 身分解析 | 不可宣稱 RFM/CLV 正確 —— 同人多卡會被算成兩個低頻顧客（見 18-G1）| 報告必須標「本分析假設 ID 已唯一，未做身分解析」|
| **D2 交易域** `fact_transaction` / `dim_product` | 交易明細、產品編碼 | RFM、CAI、CRI、購物籃、成長分解 —— 幾乎全部 M8 | 只剩問卷型或行為型分析 |
| 　└ 缺 `txn_type` 欄 | 退貨/取消標記 | **R 與 F 不可信**：退貨列會污染 R（一年沒買的人辦退貨 → R=6 天 → 被算成「冠軍客戶」）；換貨在 F 上多算 2 次（見 18-G2、gap D8）| RFM 可做但必須標「R 未排除退貨」|
| 　└ 缺 `dim_product` 品類層 | 產品屬性 | 品類角色分析、因素分析（**因素分析必須在品類層 15–16 類，不是 SKU 層**，見 18-E12）| 只能做 SKU 層共現，且不得稱為因素分析 |
| **D3 時間域** `dim_date` | 日期編碼檔（含節慶、促銷檔期旗標）| 日期效應分析、季節性拆解、促銷檔期比較 | 只能做整期彙總，不能談「什麼時候」|
| 　└ `dim_date` 有缺日 | 連續日曆 | 日期效應迴歸會把零銷售日當缺值而非 0 → 週一（多門市休館）平均銷售被高估 → 「週一表現不錯，不需調整」（gap D13）| 必須用 `generate_series` 重建 |
| **D4 行銷投入域** `fact_marketing_spend` / `dim_campaign` / `dim_channel` | 投入金額、曝光、活動、通路 | **ROAS、歸因、MMM、uplift、促銷增量、預算配置** —— 行銷分析的一半。只有「有無促銷」旗標時會把旺季自然成長算成促銷功勞（見 18-G5）| 可做促銷期 vs 非促銷期的**相關性**描述，且必須標證據等級為「相關」（見 18-G6）|
| 　└ 有 D4 但缺活動層 | campaign 粒度 | 活動層 uplift、創意層比較 | 只能做通路層預算配置 |
| **D5 行為域（web）** `fact_web_event` / `dim_session` | 網站事件、session | 轉換漏斗、路徑分析、跨裝置行為、上層漏斗歸因 | 只能從交易端看結果，不能看過程 |
| **D5 行為域（POS）** `fact_store_traffic` | 人流、動線、停留 | 進店率／提袋率四象限、動線熱點、門市績效軌跡 | 只能做門市營收比較，不能拆「來的人少」還是「來了不買」|
| **D6 治理域** `dim_metric_definition` / `log_cleaning` | 指標字典、清理日誌 | 不可宣稱數字可重現；兩份報告的數字必然打架（見 18-G10）| **不可降級 —— 這個域是 M1 自己要建的，不是等別人給** |

**判定輸出的三種標記**，回報時逐條列出：

| 標記 | 意義 | 寫法範例 |
|:--:|---|---|
| ✅ | 資料充分，照做 | `✅ 做 顧客價值分群（D1+D2+D3 齊全，97/100 顧客算得出 CAI）` |
| ❌ | 資料缺該域，**明確排除** | `❌ 不做 促銷 ROI（無 D4，只有「有無促銷」旗標。硬做會把旺季自然成長算成促銷功勞）` |
| ⚠ | 可做但必須帶警語 | `⚠ RFM 可做但 R 不可信（缺 txn_type，退貨會污染 R）` |

**這張清單不是只看「有沒有這個域」，還要看「域裡有多少人算得出來」。** 跑完 §七 之後回頭補一條硬規則：**覆蓋率落在 30–60% 的指標一律標 ⚠ 並列入「僅描述」清單**，明寫「本指標只作描述性補充，不作為分群輸入變數，也不作為建議依據」。缺域是「有沒有這張表」的問題，覆蓋率是「表裡有多少人」的問題 —— 只擋前者，就會出現一份表齊全、但建議是建立在 45% 顧客身上的報告。

## 七、覆蓋率門檻

覆蓋率回答一個很簡單的問題：**這個指標，一百個顧客裡有幾個算得出來？** 它與缺失率不同 —— 缺失率是欄位層的，覆蓋率是**指標層**的，而指標常常需要好幾個欄位同時可用、還要滿足最低樣本要求。

$$
\mathrm{coverage}(m) \;=\; \frac{\bigl|\{\, i \in P \;:\; m_i \text{ 可計算（含最低樣本要求），且未被哨兵/除零規則排除} \,\}\bigr|}{|P|}
$$

其中 $P$ 是**分析母體**（通常是顧客集合），分母固定用 $|P|$ —— **不准偷偷把算不出來的人移出分母**，那會讓覆蓋率永遠 100%。

門檻有兩個軸，**不是一條線**：能不能進報告是一回事，能不能拿去當分群輸入或建議依據是另一回事。只看其中一軸就會出現「覆蓋率 45% 的 CAI 照樣被丟進 K-means」這種事。

| 覆蓋率 | ① 能不能進報告 | ② 能不能當分群輸入／建議依據 | 出處 |
|---|---|---|---|
| ≥ 80% | 正常使用 | ✅ 可 | — |
| 60% – 80% | **可用，但報告中該指標旁必須標覆蓋率** | ✅ 可 | 藍圖 §S2 |
| 30% – 60% | 可用，但**只能當描述性補充**，圖表標題必須帶「（僅 N 人／覆蓋率 X%）」 | ❌ **不得作為分群輸入變數，也不得作為建議依據** | BT-07 硬規則；同 `01_商業框架與提問.md` §四、`09_行銷_顧客價值.md` §1.1 |
| **< 30%** | **不准進報告。** 要用必須先說明為什麼低、以及低覆蓋的那群人是不是系統性不同的一群 | ❌ | 藍圖 §S2；S2 的典型台詞是「這個指標覆蓋率只有 22%，不准進報告」|

標覆蓋率的寫法：「平均 CAI = 1.13（覆蓋率 97%）」。

**60% 這條線是逐指標的，不是通用值。** BT-07 門檻表：λ/MLE、CAI/WMLE、CRI 都是 **≥60%**，**CLV（BG/NBD）是 ≥70%**，R/M/F 則沒有覆蓋率門檻（只要 `n_txn ≥ 1`）。逐指標的最低資料需求與門檻見 `09_行銷_顧客價值.md` §1.1 的 L1–L5 表，M1 這裡只負責**算出覆蓋率並套上面這張表**，不重寫逐指標門檻。

**60% 這個數字的理由**：低覆蓋率的指標算得出來、畫得出圖、跑得出 p 值，於是名單被誤讀成母體。完整案例（汽車經銷商 2,400 位車主、CAI 覆蓋率 3.0%、18 人名單被讀成「全庫只有 18 人有流失風險」、**140 萬**產值代價）寫在 `01_商業框架與提問.md` §四，這裡不重寫。

**30% 這個數字的理由**（不是統計學常數，是決策可行性倒推）：行銷提案的最後一步是產出**可觸及的名單**。覆蓋率 30% 意味著即使指標本身完全正確，也只有三成顧客能被這條建議涵蓋，剩下七成要另外處理 —— 這時候「這個指標告訴我們什麼」已經不如「為什麼七成的人算不出來」重要。低覆蓋率是資料問題的徵狀，不是可以標註了事的免責聲明。

**覆蓋率下降的三個典型來源**（每一個都要分開報，不要只報一個總數）：

| 來源 | 例 | 這批人是不是系統性不同？ |
|---|---|---|
| 欄位缺值 | 沒有手機號 → 簡訊觸及不到 | **是**。舊會員留手機的比例低於新會員 |
| 最低樣本要求 | 間隔型指標要 $n_i \ge 3$（即 ≥2 個間隔）才算得出，要 $n_i - 1 \ge 5$ 才可信。$n_i = 2$ 時 WMLE ≡ MLE、CAI 恆為 0，是零資訊不是穩定 | **是**。低頻顧客被系統性排除 → 「我們的顧客都很活躍」的假結論 |
| 品質規則排除 | 哨兵值、除零、測試交易、bot | 視規則而定，但**必須列出排除筆數與占比**（見 18-E22）|

```sql
-- checks/coverage__customer_metrics.sql
-- 每個要進報告的指標都要跑。分母固定 = 分析母體人數，不准移出算不出來的人。
WITH pop AS (SELECT 客戶ID FROM customers),                       -- |P| = 100
     m   AS (
       SELECT c.客戶ID,
              -- R/F/M：只要有 1 筆交易就算得出來
              max(CASE WHEN t.客戶ID IS NOT NULL THEN 1 ELSE 0 END) AS has_rfm,
              -- CAI：需要 ≥3 個去重消費日（≥2 個間隔）才算得出。門檻出處：
              --   gap-business-translation.md BT-07 門檻表「CAI/WMLE：去重後天數 ≥ 3（需 2 個間隔）」，
              --   與 00 §五、09 §1.1 同一個定義。**不准放寬成 ≥2 天** —— 只有 1 個間隔時
              --   WMLE = (1·int)/1 = int = MLE，CAI ≡ 0 是代數恆等式，不是「節奏很穩」。
              --   實測：客戶 18700、18841 各只有 2 個消費日，課程 Step 5 給的 CAI 正好都是 0.0；
              --   依 17 §4.2 的 NORM.DIST(μ=0, σ=15) 轉換，這兩人會被貼成第 50 百分位的
              --   「節奏最穩定」中位顧客 —— 他們其實只是沒資料。這是靜默誤標，不只是覆蓋率數字。
              CASE WHEN count(DISTINCT t.刷卡日期) >= 3 THEN 1 ELSE 0 END AS has_cai,
              -- 可信 CAI：間隔數 ≥5，即 ≥6 個消費日（profile §2.8 評註：2–4 個間隔算出的 CAI
              --           極不穩定，一次偶發消費就能讓客戶衝上榜首，例如客戶 1611 只有 2 個間隔）。
              --           09 §1.1 的「覆蓋率 ≥60%」門檻用**這一層**判定進不進分群輸入。
              CASE WHEN count(DISTINCT t.刷卡日期) >= 6 THEN 1 ELSE 0 END AS has_cai_reliable
       FROM pop c LEFT JOIN transactions t USING (客戶ID)
       GROUP BY c.客戶ID
     )
SELECT 'R/F/M'        AS metric, sum(has_rfm)::DOUBLE          / count(*) AS coverage FROM m
UNION ALL
SELECT 'CAI',                    sum(has_cai)::DOUBLE          / count(*)             FROM m
UNION ALL
SELECT 'CAI（間隔≥5）',           sum(has_cai_reliable)::DOUBLE / count(*)             FROM m;
-- 【實測對照，2026-07-27 於 local/資料集剖析/samples/ntu_creditcard__*.parquet 實跑】
--   R/F/M           100/100 = 100%
--   CAI（≥3 消費日） 97/100 =  97%   ← 排除 6687（1 筆交易）、18700、18841（各 2 個消費日）
--   CAI（間隔≥5）    89/100 =  89%   ← 這一層才是 09 §1.1「覆蓋率 ≥60%」的判定對象
-- 兩個覆蓋率都要報，不准只報寬的那個。舊版本文件寫「CAI 覆蓋率 99%」是用 ≥2 消費日算的，
-- 那個門檻已於 2026-07-27 廢止（理由見上方 has_cai 的註解），保留此行僅供對照舊報告。
```
