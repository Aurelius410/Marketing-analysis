## 1. 環境：Python 3.14.1 是最大的隱形地雷

這是本次調研最重要、也最出乎意料的發現。**不是印象，是 `pip install --dry-run` 在這台機器上的實測結果。**

| 套件 | 在 Python 3.14.1 的實測結果 | 危險程度 |
|---|---|---|
| **dowhy** | **靜默降版到 0.8（2022 年版本）** —— pip 顯示「成功」，但因為 0.14 的 metadata 寫死 `Requires-Python >=3.9,<3.14`，pip 一路往回退。**不會警告。** | 🔴 最危險 |
| **EconML** | 安裝失敗（`ERROR: Unknown compiler(s)`，無 cp314 wheel，退回原始碼編譯） | 🟠 |
| **google-meridian** | 安裝失敗（相依 TensorFlow < 2.21，TensorFlow 無 cp314 wheel） | 🟠 |
| **Great Expectations** | `requires_python = <3.14`，直接裝不起來 | 🟡 已改用 pandera |

### 定案：雙環境策略

```powershell
# 主環境（現有 Python 3.14.1）— 統計 + 倉儲 + 交付，涵蓋日常 85% 工作
pip install duckdb pyarrow polars pandera
pip install scikit-posthocs lifelines scikit-survival statsforecast
pip install mlxtend factor_analyzer pymc-marketing tea-tasting
pip install altair great-tables vl-convert-python jinja2 xlsxwriter

# 次環境（另建 Python 3.12 venv）— 只在做因果推論 / Meridian MMM 時切過去
py -3.12 -m venv .venv-causal
.venv-causal\Scripts\pip install dowhy econml causalml google-meridian
```

**兩個環境用 Parquet 傳資料。** 這正好呼應倉儲層的定案 —— Parquet 是兩個 Python 環境的共同語言，這是分環境策略能成立的關鍵，不是妥協。

> **寫進 Skill 的硬規則**：任何時候要用 `dowhy` / `EconML` / `meridian`，先確認在 `.venv-causal`。在主環境 `import dowhy` 成功**不代表**版本正確。

## 2. 倉儲層（定案）

| 層 | 選擇 | 版本（查證日 2026-07-26） |
|---|---|---|
| 查詢引擎 | **DuckDB** | 1.5.5（cp314 wheel 已備） |
| raw / staging 儲存 | **Parquet + zstd + Hive partition** | — |
| mart 儲存 | **DuckLake**（規格 1.0，需 DuckDB ≥1.5.2） | `MERGE INTO` 給 idempotency、snapshot 給可稽核性 |
| 編排 | **純 SQL 檔 + ~100 行 Python runner** | 跨過臨界點再升級 SQLMesh |
| 品質（主力） | **純 SQL 斷言**（資料在 DuckDB 裡就在那裡驗） | — |
| 品質（出口） | **pandera** | 0.32.1（MIT，唯一明確支援 Python 3.14） |
| 輔助整形 | **Polars** | 1.43.0（abi3 wheel） |

**條件性採用**：`dlt` 1.29.1 —— 當開始打 API（Meta/Google Ads、GA4、電商平台）時加入，有原生 `ducklake` extra；檔案來源不要用它。`SQLMesh` 0.236.1 —— 專案複雜度跨過臨界點時直接上，**跳過 dbt**。

### 明確不用（都有決定性理由）

| 不用 | 理由 |
|---|---|
| **Great Expectations** | Python 3.14 裝不起來；治理型功能對一人專案無價值 |
| **Soda Core** | **Elastic License 2.0，非開源**，含 license key 機制且條款禁止規避 |
| **dbt-duckdb** | adapter 落後 core 5 個月／2 個 minor 版本，且 `dbt-core>=1.8.0` 無上限 pin，pip 會裝出未驗證組合；dbt-core 2.0 已在 alpha |
| **Ibis** | 在「SQL 為介面」的前提下是淨增加的抽象層（debug 對象變成「Ibis 表達式 → 生成的 SQL」）；12.0.0 已 5.5 個月無新版 |
| **Kedro / Hamilton** | 核心價值隨團隊人數增長，一個人用是純開銷 |
| **Iceberg 作為寫入路徑** | DuckDB 官方明述無 catalog 時**唯讀**；`pyiceberg 0.11.1` 無 cp314 wheel |

### DuckDB 實務地雷（寫進 references）

- `INSTALL encodings; LOAD encodings;` —— **Big5/CP950 必備**（台灣資料日常）
- `APPEND` 重跑必然重複 → 日常載入一律 `OVERWRITE_OR_IGNORE` + 明確日期範圍
- **明細資料上禁用 `PIVOT`** —— 官方明述內部用 `list()`，而 `list()` 不支援 spill to disk，大表必 OOM。只在已聚合的小結果上 pivot
- **`.duckdb` 不可放 OneDrive / 網路磁碟機** —— 官方明確建議避免，會有檔案鎖衝突
- `hour=` 分區太細（每小時 3–6MB，遠低於官方建議的 100MB/partition）

## 3. 統計層：R → Python 已實測通過

**statsmodels 0.14.6 有 cp314 wheel，已裝在這台機器上。** 調研 agent 實際跑過一份涵蓋 `lm`/`glm`/`anova_lm(typ=1,2,3)`/Cook's D/槓桿值/VIF/巢狀 F 檢定/Tukey HSD/殘差診斷檢定/MixedLM/quantreg 的驗證腳本，**全部通過**。

R 統計課那套 **95% 可一比一搬過來**。唯一真正的缺口是 `emmeans`，用 `t_test()` + 對比向量可手工補上（調研文件 A.9 節有實測過的可用程式碼）。

### 🔴 一個會靜默算錯的陷阱

**`anova_lm(typ=3)` 搭配預設 treatment coding 會靜默算出錯誤的主效果 SS**（實測差近一倍）。必須用 `C(x, Sum)`。

這不是套件 bug，是用法問題，但危害同等嚴重 —— 它不會報錯，只會給你錯的數字。**必須寫成 Skill 的防呆函式 `anova3(formula, data)`，不讓使用者直接呼叫 `anova_lm(typ=3)`。**

### 專案自製模組 `src/stats_utils.py`（R→Python 遷移的真正資產）

| 函式 | 取代的 R 功能 |
|---|---|
| `plot_lm(model)` | `par(mfrow=c(2,2)); plot(lm)` 殘差診斷四圖 |
| `vif_table(model)` | `car::vif`（GVIF 表） |
| `anova3(formula, data)` | 防呆 Type III（強制 `C(x, Sum)`） |
| `emmeans(model, data, factor)` + `emm_contrasts(...)` | `emmeans` 套件 |

## 5. 視覺化與設計層

### 5.1 一個實測結論推翻了通用建議

調研實測發現：**沒有現成色盤能同時通過對比度與色盲（CVD）門檻**。

- 原封不動的 Okabe-Ito 8 色：實測白底對比 1.32 / 2.25 / 2.31，**三色當線條完全不可見**
- Tableau Color Blind 10：normal 視覺下最小 ΔE 僅 10.8（兩個灰撞色），8 色中 4 色對比不足
- 深色主題用完整 viridis：低端 `#440154` 對 `#14181F` 對比 **1.17:1，等於看不見**

**因此定案：自建 token（Okabe-Ito 色相邏輯 + OKLCH 導出深色版），並附一支 `palette_lab.py` 把美感變成可跑的測試。**

### 5.2 字型

| 用途 | 字型 | 理由 |
|---|---|---|
| 主字型 | **Noto Sans TC**（OFL，已安裝） | **唯一同時滿足可商用、可嵌入、數字等寬（0.521 em）的繁中黑體** |
| 補靜態字重 | Noto Sans TC subset OTF 七字重 / Source Han Sans 2.005R | 解 matplotlib 可變字型無粗體問題 |

**不可用**：Microsoft JhengHei 嵌入交付檔（Windows 隨附授權，不可自由嵌入散布，僅限本機產出）；Noto Serif TC 排數字欄（實測數字有 6 種寬度，非等寬）。

⚠️ 實測：**Noto Sans TC / Noto Serif TC / JhengHei 都沒有 `tnum` feature**，所以 `font-feature-settings: "tnum"` 不是解法 —— 要靠選對字型本身。

### 5.3 交付堆疊

| 用途 | 選擇 |
|---|---|
| 靜態圖（含統計診斷圖） | **matplotlib + `.mplstyle`** |
| 互動圖 | **Altair + `alt.theme.register`**（注意：`alt.themes.register()` 5.5 起 deprecated） |
| 靜態匯出 | **vl-convert-python**（Altair→PNG/PDF，不需 node） |
| HTML 表格 | **great-tables** |
| Excel 表格 | **XlsxWriter**（格式碼）+ openpyxl（讀改）—— 數值必須存成數值型別 + 原生格式碼 |
| 單檔 HTML 報告 | **Jinja2**（內嵌 CSS token + base64 圖） |
| 圖表分類法 | FT Visual Vocabulary 繁中版 |
| 商業表示法 | **ISO 24896 / IBCS 2.0**（2026-06-11 成為國際標準） |

**明確不用**：plotly.py（單檔 HTML 會塞入約 3MB 的 plotly.js）、雙 Y 軸（除單位換算外，縮放可任意調整→可製造任意相關性）、圓餅 >5 類、雷達圖、3D。

## 6. 防呆規則庫（實證導出，直接寫進 Skill）

這是報告文體調研最有價值的產出：它解剖了 **214 份 PDF**，並用成績檔的「備註」欄**反推出扣分規則**。

### 6.1 風險模型（實證等第對應）

| 缺失 | 判給等第 | 人數 |
|---|---|---:|
| 全部 11 項齊全 + 篇幅充足 | **A+** | — |
| **僅缺事後檢定，止於 ANOVA** | **A** | **27 人** |
| 缺任一單項分析（CAI / CRI / F檢定 / 購物籃因素分析） | A- | 14 人 |
| 全項齊全但篇幅 ≤11 頁 | A- | 3 人 |
| 缺一整段統計檢定，或缺顧客價值核心模組 | B+ | — |
| 非報告格式 + 缺多項 + 篇幅 4 頁 | C+ | — |

> **最關鍵的一行**：27 個人（全班第二大扣分群）**只因為漏了「事後檢定」一項**，就從 A+ 掉到 A。
> **事後檢定是最容易漏、漏了成本最高的單一步驟。**

### 6.2 致命級錯誤（Skill 必須硬性阻擋）

| # | 錯誤 | 防範規則 |
|---:|---|---|
| **E1** | **ANOVA 做完就停，漏掉事後檢定** | pipeline 強制 `ANOVA → 事後檢定` **綁定，不可分離** |
| **E2** | 用人口統計變數做分群 | **分群變數白名單**：R/F/M/RFM Score/CAI/CRI/因素分數/LN_F/LN_M。人口變數只能出現在卡方那一章 |
| **E3** | 報告中途結束，沒有結論章 | 產出前檢查 11 章 checklist 全綠 |
| **E4** | 無封面/目錄/頁碼 | 模板固定件，不可關閉 |
| **E5** | 篇幅嚴重不足 | 目標 25–35 頁，<20 頁觸發警告 |

### 6.3 嚴重級錯誤（自動檢查）

| # | 錯誤 | 防範規則 |
|---:|---|---|
| **E6** | 術語錯誤（實例：CAI 誤植為 Category Expansion Index） | 內建術語表校驗：**CAI = Customer Activity Index**、**CRI = Customer Reliability Index** |
| **E7** | **圖文數字矛盾**（實例：圖標「女 75.2%」，內文寫「女性佔 24.8%」） | 所有內文數字**必須從同一份計算結果物件產生，不得手打** |
| **E8** | 公式抄錯（實例：`BE = w1·GE × w2·IE`，應為加號凸組合） | 公式庫集中管理，不逐份手寫 |
| **E9** | 表格數值異常未察覺（實例：ANOVA 表一格 `3217.258`，同欄其他值在 3.2~3.5） | 產表後**自動離群掃描：同欄數量級差 >100 倍即警告** |
| **E10** | **相關係數 = 1.00 卻不質疑**（實例：Top 12 購物籃組合 r 全部 = 1，因在單一小類下用稀疏二元共現算 Pearson） | 相關矩陣須設**最低共現次數門檻（n≥5）**，r=±1 一律標記「樣本不足，不可解讀」 |
| **E11** | 因素分析適配不佳就整章刪掉 | 適配不佳 → **保留章節 + 報告適配指標 + 說明替代方案** |
| **E12** | 在錯誤粒度做因素分析（實例：對個別 SKU 而非品類） | 因素分析在**品類層級（15–16 類）**，不是 SKU 層級 |

### 6.4 中度級（影響豐富度）

E13 直接貼統計軟體輸出 → 一律重繪｜E14 跨頁表格未重標表頭｜E15 統計表沒有商業解讀欄 → **每張統計表強制最後一欄為中文結論**｜E16 「不顯著」就不寫 → **不顯著要列表、要寫商業意涵**｜E17 只挑顯著的秀 → 所有群×所有變數都要出現，不顯著標「—」｜E18 放寬 α 卻不聲明｜E19 小結寫成「本章分析了 XX」 → **小結公式 = 發現（帶數字）+ 經營意涵 + 承接下一章，150–400 字**｜E20 策略建議空泛 → **每個策略必須含：統計依據（帶 p 值/係數）+ 具體通路 + 具體優惠數字 + 目標客群編號**｜E21 不寫「該停止做什麼」 → A+ 報告都有負面建議｜E22 樣本數變化未交代

## 7. 需要包子決定的事

### 決策題 A：報告產製走 Jinja2 還是 Quarto？

| | **Jinja2 單檔 HTML** | **Quarto** |
|---|---|---|
| 依賴 | 純 Python，無外部 CLI | 需裝 Quarto CLI（含 Pandoc） |
| 單檔 HTML | ✅ 完全可控（base64 內嵌） | ✅ `embed-resources: true` |
| 投影片 | ❌ 要另用 python-pptx | ✅ 同一份原始檔出 revealjs |
| PDF | ❌ 要另接 WeasyPrint | ✅ 內建 |
| 跨頁表頭重標 | 需自己處理 | ✅ 有現成解法 |
| 模板現況 | 要從零寫 | **報告文體調研已給完整骨架** |

我的建議：**先做 Jinja2 單檔 HTML（主線交付物、依賴最少、最可控），投影片用 python-pptx**。Quarto 列為可選加值，等真的覺得投影片與 PDF 很痛再裝。理由是四種交付物裡，「單檔 HTML」是包子最常用的，而它恰好是 Jinja2 最強、Quarto 沒有優勢的那一項。

### 決策題 B：儀表板方案（尚未調研）

Evidence.dev / marimo / Streamlit 的取捨還是空白，那支 agent 死在限額。要不要等限額重置後補跑一支專門調研儀表板？

### 決策題 C：還缺的三份缺口分析要不要補？

資料工程 / 統計推論 / 商業轉譯三視角的獨立審查全部沒跑成。藍圖 v1 §5 的 16 條缺口是我自己列的，沒有經過第二雙眼睛挑戰。
