## 0. 這份文件要解決什麼

包子要的最終狀態是一句話：

> **把資料丟進去 → 一連串的討論與分析過程 → 拿到分析報告與儀表板。**

這句話裡有三個不能混為一談的東西：

| 元素 | 本質 | 設計重點 |
|---|---|---|
| 「把資料丟進去」 | 資料工程問題 | 進場檢核、倉儲分層、指標口徑單一真相 |
| 「一連串的討論」 | 決策流程問題 | 卡點在哪、問什麼、誰決定 |
| 「報告與儀表板」 | 交付與美感問題 | 文體、圖表選型、視覺系統 |

三者要靠**同一套資料模型**串起來，否則會變成三個彼此打架的子系統。這份藍圖的核心主張就是：**先把資料模型釘死（四大資料檔），其餘全部掛在它上面。**

**衝突點與裁決：**

1. **IB5082 說「檢查計算過程不檢查答案」，MBA5045 說「假設不成立結論就無效」。**
   → 裁決：兩者都要。Skill 要同時輸出「計算過程軌跡」與「假設檢查結果」，且**假設不成立時必須降級並說明**（沿用 HW8 的「沒有備案才是扣分點」）。

2. **IB5082 直接從相關性跳到行銷建議，MBA5045 明說觀察型資料只能談關聯。**
   → 裁決：報告的「行銷決策建議」章節必須標註**證據等級**（相關／預測／準實驗／實驗），不能讓讀者誤以為是因果。這是我要新增的一層，兩份教材都沒有。

3. **IB5082 的分群用人口統計描述輪廓；L1 又說「要用行為本質不用成員結構」。**
   → 裁決：**分群輸入變數用行為指標（RFM/CAI/CRI/購物籃因素分數），人口統計只用於事後輪廓描述與檢定**。這正是 HW8 的做法，把它固化成硬規則。

## 3. 核心資料模型（框架的地基）

任立中第 2 講的四大資料檔，本質就是一個標準星狀模型。這是整個框架的地基，**所有指標、所有分析、所有圖表都從這裡長出來**。

```
                    dim_customer  （客戶基本靜態資料檔）
                    會員號碼 PK
                    ├ 識別：會員號碼、登記日期
                    ├ 人口統計：生日、性別
                    ├ 社經：教育程度、職業、職位、年收入、居住型態
                    ├ 家庭：家庭成員、生命週期
                    ├ 心理：生活型態、人格特質、休閒活動、嗜好
                    └ 偏好：資訊收受種類、消費通路型態
                              │
                              │
  dim_date ───────────  fact_transaction  ─────────── dim_product
  日期 PK               （客戶購買動態資料檔）          產品序號 PK
  ├ 星期 7 個 0/1        grain = 發票明細一列一品項      ├ 外國/本國知名廠牌
  ├ 週休二日             PK = 店別+日期時間+電腦序號      ├ 製造來源國
  ├ 連續假期                  +發票號碼+產品序號         ├ 外觀樣式
  ├ 春節/國定假日        ├ 交易核心：日期、金額、數量     ├ 產品功能
  ├ 特殊節日             ├ 價格：單價、折扣、贈品         ├ 相對價格
  ├ 氣候：溫度/雨/颱風    ├ 動機：購買成因、性質          └ 上架日期
  ├ 公司促銷活動         ├ 行銷刺激：促銷活動內容
  └ 競爭者活動           ├ 收款：付款方法、收款日期
                        ├ 物流：配送方式、日期
                        ├ 信用：信用額度、賒帳餘額
                        ├ 成效：成交、退貨量
                        └ 售後：滿意度、報怨處理
```

**三條來自講義的硬約束：**

1. **日期維度表一天一列、連續不跳號** —— 交易可為零，但日期列必須存在，否則無法估計「不購買」的機率。
2. **事實表必須是長格式**（一列一筆交易明細），才能同時 pivot 出橫斷面與縱斷面（「縱橫交錯」）。
3. **四檔缺一不可** —— 只有顧客檔＋交易檔的資料庫做不了日期效應與產品屬性偏好分析。這是最常見的缺漏。

### 3.1 從四大資料檔擴充成六域模型

包子已確認未來**四種資料型態全都會遇到**：會員/CRM 交易、電商/網站行為、廣告投放成效、實體零售 POS/門市。四大資料檔只涵蓋第一種，必須擴充。

好消息是：**擴充方向講義自己就給了**。L2 p.19–20 的店內感測（人流、動線、停留時間、觸碰次數）與 p.28–29 的進店率／提袋率四象限，本來就是 POS/門市域；p.39 的「促銷活動內容」欄位則是行銷投入域的殘影。我只是把講義點到為止的東西補成完整的表。

| 域 | 表 | 來源 | 涵蓋的資料型態 |
|---|---|---|---|
| **D1 顧客域** | `dim_customer`（靜態檔）<br>`map_identity` ⭐新增 | 講義 p.31 / 新增 | 全部 |
| **D2 交易域** | `fact_transaction`（動態檔）<br>`dim_product`（產品編碼檔） | 講義 p.39 / p.52 | CRM、電商、POS |
| **D3 時間域** | `dim_date`（日期編碼檔） | 講義 p.45 | 全部 |
| **D4 行銷投入域** ⭐新增 | `fact_marketing_spend`<br>`dim_campaign`、`dim_channel`、`dim_creative` | 新增（講義只有旗標） | 廣告、電商 |
| **D5 行為域** ⭐新增 | `fact_web_event`、`dim_session`<br>`fact_store_traffic`（人流/動線/停留） | 新增 / 講義 p.19–20 | 電商、POS |
| **D6 治理域** ⭐新增 | `dim_metric_definition`（指標字典）<br>`log_cleaning`（清理日誌） | 新增 | 全部 |

**三張新增表的理由（每一張都對應一類會做錯的決策）：**

| 新增表 | 沒有它會怎樣 |
|---|---|
| `fact_marketing_spend` + `dim_campaign/channel` | 四大資料檔只有「有無促銷」旗標，沒有投入金額與曝光。**沒有它就做不了 ROAS、歸因、MMM、uplift** —— 行銷分析等於少了一半，而且會把旺季自然成長算成促銷功勞。 |
| `map_identity` | 真實資料的顧客 ID 不乾淨：同人多卡、多裝置、跨通路帳號、退換貨衝銷、內部測試帳號。教材假設 ID 乾淨，真實專案第一天就炸。 |
| `dim_metric_definition` | RFM 的基準日？M 要不要扣退貨？F 是交易數還是品項數？**指標定義必須是資料，不是散落在程式碼裡的常數**，否則兩份報告的數字會打架。 |

### 3.2 分域啟用（degraded mode）

不是每個專案四種資料都有。Skill 在 S2 體檢後要**明確宣告哪些域有資料、因此哪些分析可做／不可做**：

| 有的域 | 可做 | 明確不可做 |
|---|---|---|
| D1+D2+D3（四大資料檔） | RFM/ARFM、CAI、CLV、購物籃、分群與輪廓檢定、日期效應 | 任何涉及行銷投入 ROI 的結論 |
| ＋D4 | ROAS、歸因、促銷增量、預算配置 | — |
| ＋D5（web） | 轉換漏斗、路徑分析、跨裝置行為 | — |
| ＋D5（POS） | 進店率/提袋率四象限、動線熱點、門市績效軌跡 | — |

**硬規則：缺少某一域時，報告必須明寫「本分析無法回答 X 類問題」，而不是用手邊有的資料硬答。**

## 4. 分析管線：八個階段

沿用任立中「八步」的形式，但改寫成可執行的資料管線。**包子已選擇高卡點密度：每一階段結束都回報一次。**

```
S1 開案對焦 ─▣─ S2 進場剖析 ─▣─ S3 清理建倉 ─▷─ S4 指標工程 ─▣─
                                                                    │
S8 歸檔 ─▷─ S7 交付 ─▷─ S6 驗證與自我攻擊 ─▣─ S5 分析執行 ─▷──────┘

▣ = 硬卡點（等包子回覆才往下）      ▷ = 回報點（回報後預設繼續，包子喊停才停）
```

### 4.0 卡點設計：八個回報點，四個硬卡點

| 階段 | 型態 | 回報內容 | 為什麼是這個型態 |
|:--:|:--:|---|---|
| S1 | **▣ 硬卡點** | Check List 矩陣、產業定位、成熟度目標、證據等級目標 | 問錯問題，後面全白做 |
| S2 | **▣ 硬卡點** | 資料體檢報告、六域缺口盤點、**因此建議做／不做哪些分析** | 整條管線最重要的一關 |
| S3 | ▷ 回報點 | 建倉結果、清理異動清單（刪了幾列、為什麼）、星狀模型完整度 | 清理規則已在 S2 談定，這裡是執行回報 |
| S4 | **▣ 硬卡點** | 指標分布圖、極端樣本、**口徑確認**（基準日／退貨／F 的定義） | 口徑錯了，所有數字都要重算 |
| S5 | ▷ 回報點 | 各分析的初步結果與可疑點 | 結果本身不需要授權，但要讓包子有機會轉向 |
| S6 | **▣ 硬卡點** | 通過的檢查／失敗的檢查／**因此降級的結論** | 決定報告能主張到什麼程度 |
| S7 | ▷ 回報點 | 四種交付物的產出清單與預覽 | — |
| S8 | ▷ 回報點 | 分析紀錄、環境快照、資料指紋 | — |

**回報格式統一**（沿用既有 skill 的「異動清單」精神）：每次回報都是「做了什麼 → 發現什麼 → 因此建議什麼 → 需要你決定什麼（若無則寫「無，繼續」）」四段。

### S1 開案對焦（Frame）— 決策倒推，禁止從資料開始

執行任立中的**七問倒推鏈**，填出 Check List 矩陣：

| 管理者需要做的決策： | A | B | C | D | E |
|---|---|---|---|---|---|
| 每一種決策所需要的資訊是什麼？ | | | | | |
| 各項資訊要透過何種分析方法獲得？ | | | | | |
| 各式分析方法所需之資料型態為何？ | | | | | |
| 如何定義資料庫中的各個欄位？ | | | | | |
| 資料從哪裡來、怎麼蒐集？ | | | | | |

**規則：任一格填不出來 ⇒ 該決策目前不被資料支援，必須補欄位或明確放棄。**

同時做三件事：
- **產業定位診斷**（客戶對象／數量／類型／購買頻度／購買內容五維）→ 決定分析深度上限。低頻產業（汽車、旅館）的 R/F 統計效力薄弱，要改走靜態變數與生命週期事件。
- **成熟度目標宣告**：這次交付要停在 BI（現況）、CI（情境化效果）還是 DI（模擬與建議）？**停在 BI 就只是報表，不算分析交付。**
- **證據等級目標**：這次能做到相關、預測、準實驗、還是實驗？

> **卡點①**：把 Check List、產業定位、成熟度目標、證據等級整理成一頁，跟包子確認後才動資料。

### S2 資料進場與剖析（Profile）

先看，不要先洗。輸出一份 **資料體檢報告**：

- 檔案清單、格式、編碼、大小、sheet 結構（含隱藏分頁、文字方塊、儲存格註解 —— 沿用既有 skill 的六位置全掃思路）
- 每欄：型別推定、缺失率、唯一值數、數值五數摘要、類別 top-10、日期 min/max
- **粒度判定**：一列到底代表什麼？主鍵候選是誰？重複列多少？
- **可疑訊號**：全形半形混用、幣別單位不明、時區、負值金額（退貨？）、測試帳號特徵、日期跨界
- **對照四大資料檔做缺口盤點**：哪些欄位有、哪些沒有、沒有的話哪些分析要被砍掉

> **卡點②**：把體檢報告 + 缺口盤點 + 「因此建議做／不做哪些分析」給包子確認。**這是整條管線最重要的卡點** —— 錯在這裡，後面全錯。

### S3 清理與建倉（Warehouse）

```
│   └── stg_transaction/dt=2026-07/part-0.parquet
├── 03_mart/           ← 四大資料檔（星狀模型），分析的單一真相

    └── customer_features.parquet
```

清理動作全部寫成 **SQL 檔**（`sql/02_staging/*.sql`、`sql/03_mart/*.sql`），可重跑、可 diff、可版控。Python 只負責讀不進 SQL 的東西（Excel 怪版面、PDF、爬蟲）。

**每一步都要留下「清掉了什麼、為什麼、影響幾列」的清理日誌** —— 這是既有 skill 的「異動清單」精神。

### S4 指標工程（Metrics）

從 `03_mart` 算出顧客層寬表。指標分四組：

| 組 | 指標 | 來源 |
|---|---|---|
| **基礎 RFM** | R、F、M（三種算法可切換：土法／樞紐／函數） | IB5082 HW3 |
| **加權與分位** | Bob Stone 原版／自訂權重、五等分法、三法排名比較 | IB5082 HW3 |
| **動態指標** | λᵢ（平均購買間隔）、MLE、WMLE、**CAI**、Recency/λᵢ（標準化流失訊號） | IB5082 HW4 + L2 p.48 |
| **價值指標** | μᵢ、貝氏收縮平均、CRI、CLV | IB5082 HW5 |
| **結構指標** | 購物籃因素分數、品類偏好向量、通路偏好 | IB5082 HW6/HW7 |
| **ARFM 標籤** | 四維二分交叉 → 16 類 | IB5082 L2 p.42 |

**每支指標腳本都要對課程資料集跑迴歸測試**（客戶 89 的 R=19/F=85/M=150681、CAI≈−12.56 等），確保實作正確。

> **卡點③**：指標算完先給包子看分布圖與異常樣本，確認口徑（基準日、退貨處理、極端值）後才進建模。

### S5 分析執行（Analyze）— 依成熟度分層

```
BI 層（現況）      樞紐交叉、趨勢、例外報告、四象限定位
   │                Corr(X₁,X₂)
   ▼
CI 層（情境化）    迴歸／GLM／分群／關聯規則／因素分析
   │                Y = α + β₁X₁ + β₂X₂ + ε，其中 βᵢ = γZ + δ
   ▼
DI 層（模擬）      What-if、uplift、CLV 預測、投放配置最佳化
                    Prob(X = x) = ?
```

**異質性／動態性強制檢核**（任立中的公理）：
- 模型只有單一全域 β ⇒ 你同時假設掉了異質性與動態性 ⇒ 「naive statistical model」
- 需要 βᵢ → 階層／隨機係數模型
- 需要 βₜ → 時變參數
- 兩者都要 → panel model

分群鐵律：**輸入變數用行為指標，人口統計只用於事後輪廓描述與檢定。**

### S6 驗證與自我攻擊（Validate）

這是三套教材裡最薄弱、我認為最該補強的一環。分三道：

**第一道 — 統計假設（來自 MBA5045）**
殘差常態性／變異數同質／獨立性、共線性 VIF、槓桿點與 Cook's D、巢狀模型 F 檢定、GLM 的 Deviance 配適、多重比較校正（FDR）。

**第二道 — 資料陷阱（教材都沒有）**
- 生存者偏誤：只看還活著的顧客算 CLV
- 辛普森悖論：整體與分群結論相反
- Cohort 未對齊：不同時間進來的顧客混算，tenure 混淆成長
- 目標洩漏：用全期資料算特徵去預測期內事件
- 選擇偏誤：只有填問卷的人有態度變數（正是 f(X)=g(Z) 要解的問題）

**第三道 — 因果界線（明確標註）**
每一條行銷建議標上證據等級：`相關` / `預測` / `準實驗` / `實驗`。禁止把相關寫成因果。

> **卡點④**：把「通過的檢查／失敗的檢查／因此降級的結論」列表給包子，確認後才寫報告。

### S7 交付（Deliver）

四種交付物，同一份分析結果四種出口：

| 交付物 | 技術 | 章節／內容規格 |
|---|---|---|
| **單檔 HTML 報告** | Quarto → self-contained HTML | 11 必備章節（見下）+ 排版檢查清單 |
| **互動儀表板** | Evidence.dev（SQL 原生）或 marimo | MDSS 三層：例行趨勢／例外警示／專案模擬 |
| **投影片** | Quarto revealjs 或 pptx | KPI → 關鍵圖 → 結論 → 建議 |
| **Excel／CSV 成果檔** | openpyxl，CSV 一律 utf-8-sig | 分群名單、指標表、可直接給行銷團隊執行 |

**報告 11 必備章節（IB5082 期末報告原文規格）：**
1. 資料描述 2. RFM 模型 3. CAI 指標 4. CRI 指標 5. 購物籃分析 6. 集群分析 7. 卡方檢定 8. F 檢定/ANOVA 9. 事後檢定 10. **每章末小總結** 11. **給管理者的行銷決策建議**

**排版硬規則**：封面、摘要、目錄、頁碼、大小標、**所有表格重製不得直貼統計軟體輸出**、跨頁表頭重標、顏色只用於區別與凸顯。

## 5. 我認為現有實務不夠全面的地方（缺口清單）

這是包子明確要我思考的部分。以下每一條都對應一個「會做出錯誤行銷結論」的具體情境。

### 5.1 critical — 會直接產出錯誤結論

| # | 缺口 | 會怎麼出錯 | 修補動作 |
|---|---|---|---|
| 1 | **沒有身分解析（identity resolution）** | 同一顧客有兩張卡 → 被算成兩個低頻顧客 → RFM 全錯、CLV 低估、「流失顧客」名單裡塞滿其實很活躍的人 | S3 建 `map_identity`；提供三種比對策略（精確鍵／規則式／機率式）並要求人工抽驗 |
| 2 | **退貨與取消未處理** | M 虛胖。某顧客買 50 萬退 48 萬，被標成「高價值忠誠」丟進 VIP 名單 | 指標字典明訂 M 的口徑；預設用淨額，並輸出毛額／淨額對照 |
| 3 | **Cohort 未對齊** | 今年新客的 F 天生比三年老客低 → 「新客不忠誠」的假結論 → 錯誤地砍新客預算 | 所有顧客層指標加 `tenure_days`；分群與比較一律在 cohort 內或以 tenure 為共變量 |
| 4 | **目標洩漏** | 用全期交易算 RFM，再拿去預測「這一期會不會流失」→ 驗證集 AUC 0.95，上線後崩盤 | 特徵計算強制切 `as_of_date`；提供 `build_features(as_of)` 介面，禁止無時點的特徵 |
| 5 | **沒有行銷投入資料就談 ROI** | 四大資料檔只有「有無促銷」旗標。用它做「促銷有效」的結論，等於把旺季自然成長算成促銷功勞 | 新增 `fact_marketing_spend`；沒有這張表時，報告必須明寫「本分析無法歸因至行銷投入」 |
| 6 | **相關性直接寫成行銷建議** | 購物籃 Top1「旅遊+精品」相關 0.47 → 建議「買旅遊送精品券」。但兩者可能都只是高所得的結果，搭售不會有增量 | 建議一律標證據等級；想主張因果就要走 uplift／DiD／實驗設計 |

### 5.2 important — 會讓結論不穩或不可信

| # | 缺口 | 說明 | 修補動作 |
|---|---|---|---|
| 7 | **分群數與穩定性沒有依據** | 教材直接跑 K-means，沒講 k 怎麼定、換個亂數種子群會不會變 | 加 elbow／silhouette／gap statistic，加 bootstrap 穩定度（ARI），k 的選擇要寫理由 |
| 8 | **多重比較未校正** | HW8 要跑一堆卡方＋ANOVA＋post-hoc。20 個檢定跑下來，必有 1 個假顯著 | 統一 Benjamini-Hochberg FDR；報告同時列原始 p 與校正後 p |
| 9 | **沒有留存／存活分析** | 流失是行銷核心問題，教材只有 CAI 當代理指標，無法回答「這群人還會活多久」 | 補 Kaplan-Meier 與 Cox；CLV 用 BG/NBD + Gamma-Gamma 而非只有歷史加總 |
| 10 | **指標口徑沒有單一真相** | 基準日、M 含不含稅／退貨、F 算交易數還是品項數 —— 兩份報告數字打架 | `dim_metric_definition` 表；每張圖表底下自動標註口徑 |
| 11 | **缺資料品質關卡** | 教材全程假設資料乾淨。真實資料第一天就有編碼壞、粒度不唯一、關鍵欄全空 | `check_data_quality.py`，三桶（error/warning/info）+ exit code，error 直接擋住不准往下 |
| 12 | **全 Excel 手工，不可重現** | 樞紐拉一次、函數填一次，半年後無法重跑，也無法換一批資料重跑 | 全部程式化；SQL 與 Python 檔案化、版控 |

### 5.3 nice-to-have — 品質與長期維護

| # | 缺口 | 修補動作 |
|---|---|---|
| 13 | **PII 未處理** | 靜態檔含身分證字號、電話、住址。加去識別化層：分析用雜湊 ID，明碼只留在 `01_raw` 且不進 git |
| 14 | **圖表設計無規範** | 期末報告排版清單很好，但沒講圖表選型、色彩、色盲友善。建 `assets/theme/`：調色盤、繁中字型 fallback、圖表選型決策表 |

### 6.1 倉儲與資料處理

| 層 | 選擇 | 理由 |
|---|---|---|
| 查詢引擎 | **DuckDB** | 單機、零維運、原生讀寫 Parquet、SQL 完整度高。包子偏好 SQL，這是最直接的答案 |

### 6.2 統計建模（要把 R 的那套完整用 Python 重寫）

| 分析動作 | R 原本用法 | Python 對應 ⚑ |
|---|---|---|
| 簡單／多元迴歸 | `lm()` + `summary()` | `statsmodels.formula.api.ols`（公式介面幾乎一比一） |
| 殘差診斷四圖 | `par(mfrow=c(2,2)); plot(lm)` | 自寫 `diagnostic_plots()`：Residuals vs Fitted、Q-Q、Scale-Location、Residuals vs Leverage |
| 影響點 | `cooks.distance()` | `OLSInfluence.cooks_distance` |
| 共線性 | `vif()` | `statsmodels.stats.outliers_influence.variance_inflation_factor` |
| 巢狀模型比較 | `anova(m1, m2)` | `statsmodels.stats.anova.anova_lm(m1, m2)` |
| ANOVA / 二因子 | `aov()` | `anova_lm(ols(...), typ=2)` |
| 事後檢定 | `TukeyHSD()` | `pingouin.pairwise_tukey` ⚑ 或 `scikit-posthocs` |
| Logistic / GLM | `glm(family=binomial)` | `statsmodels.formula.api.glm(family=Binomial())` |
| 卡方檢定 | `chisq.test()` | `scipy.stats.chi2_contingency` |
| 因素分析（HW7） | SPSS | `factor_analyzer` ⚑（含旋轉、因素分數） |
| 集群分析（HW8） | SPSS | `sklearn.cluster`（KMeans／Ward）+ `scipy.cluster.hierarchy` |
| 購物籃（HW6） | Excel 樞紐 | DuckDB SQL 做矩陣 + `mlxtend` 做 apriori/FP-growth |

**要補的行銷專用套件** ⚑（維護狀態待查）：
