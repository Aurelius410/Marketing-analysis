### F2【important】`f_active_days = 68` 與由它推出的 2,216、25%，用本文件自己的 SQL 重算是錯的

- **檔案**：`references/17_指標公式庫.md` 第 61 行（並被 `04_資料體檢.md` 第 532 行、`11_行銷_成長與促銷.md` 第 70 行沿用）
- **原文引述**（17 §二）：
  > **欄名一律帶口徑後綴，禁止裸 `F` / `M`。** 因為 `F` 有三種粒度（筆數 / 消費天數 / 品項數）而數字差很多：客戶 89 的 `f_txn_cnt = 85`、`f_active_days = 68`，用前者算客單價得 1,773、用後者得 2,216，**差 25%**。
- **錯在哪**：`f_active_days` 在同一份文件 §二的 SQL 裡定義為 `COUNT(DISTINCT txn_date)`。對課程資料集實跑，客戶 89 的相異刷卡日是 **69** 天，不是 68。連帶：
  - 150,681 / 69 = **2,183.78**（文件寫 2,216，那是除以 68 的結果）
  - 真正的落差是 2,183.78 / 1,772.72 = **1.232（23.2%）**，不是 25%
  - 68 其實是**間隔數**（69 − 1）。這正是 MLE 的分母：699 天跨度 / 68 = 10.279412，與 §八 的基準值 `MLE=10.279412` 完全吻合。所以是把「間隔數」誤植成「消費天數」。
- **怎麼確認**：
  - `SELECT COUNT(DISTINCT CAST(刷卡日期 AS DATE)) FROM ntu_creditcard__transactions.parquet WHERE 客戶ID=89` → **69**（跑了兩次，含 `CAST` 與不 `CAST` 兩種寫法）
  - `date_diff('day', min, max)` = 699；699/68 = 10.279411764705882，與 `ntu_creditcard__customer_rfm_cai.parquet` 的 `mle` 欄位逐位相同
  - 150681/68 = 2215.897（→2,216）、150681/69 = 2183.78；(150681/68)/(150681/85) 恰為 1.25
- **附註（不是本 skill 原創的錯，但仍是錯）**：素材本身也是 68 ——
  `local/資料集剖析/marketing_datasets_profile.md` 第 727 行「若誤用消費天數，客戶 89 會得到 68 而非 85」、
  `research/gap-data-engineering.md` 第 352 行「150,681 / 68（消費天數）= 2,216，差 25%」。
  而同一份 gap 檔第 352 行又把間隔數寫成 67（「CAI 的間隔數（天口徑，67 個間隔）」），素材自己前後矛盾。
  真值是：**消費天數 69、間隔數 68**。
- **修法**：三處統一改為 `f_active_days = 69`、客單價 `2,184`、落差 `23%`；並在 17 §八的基準值表新增一列
  `客戶 89 口徑 | f_txn_cnt=85, f_active_days=69, n_intervals=68`，讓 `tests/test_metrics.py` 直接鎖住這組數字
  （目前若照文件寫成 68 去斷言，測試必紅）。同時在 17 §九維護條款註記「素材 profile §2 與 gap-data-engineering D19 的 68 為誤植，已更正」。

### F3【important】「λ 中位數 10.79 天」——統計量名稱錯（那是平均數），且交叉引用指向不存在的內容

- **檔案**：`references/15_實驗設計.md` 第 79、257、392 行（結尾出處欄第 478 行）

- **錯在哪**：兩件事都錯。
  1. **10.79 是平均數不是中位數**。素材原文：`marketing_datasets_profile.md` 第 647 行 `int` 欄 `min=1, q25=2, median=5, **mean=10.7944**, q75=11, max=510`；第 678 行樞紐 `Grand Total 10.794378`；`10_blueprint/03_執行脈絡 §S2` 第 164 行明寫「不排除算**平均間隔**得 199.46，真值 **10.79**」。
     實算：5,194 筆間隔的 **mean = 10.794378**、**median = 5.0**；若改取「每位顧客 λ 的中位數」則是 **15.25**。三個數沒有一個是「λ 中位數 10.79」。
  2. **出處是假的**。`17_指標公式庫.md` §4.1 只有 λ / μ / Recency / Churn Signal 四條公式，**全文沒有出現 10.79**（`grep -n "10.79" 17_指標公式庫.md` 零命中）。
- **怎麼確認**：
  - DuckDB 重算：`with d as (select distinct 客戶ID, cast(刷卡日期 as date) dt …), lead() 取間隔` → `count=5194, avg=10.794378128609935, median=5.0`（與 profile 的 5,194 列、10.794378 逐位相同）
  - `select median(mle) from ntu_creditcard__customer_rfm_cai.parquet` → **15.25**
  - `grep -rn "10.79" 00_source_archive/` → 只在 profile 與 blueprint 命中，全部語境是「平均」
- **影響**：15 用它推出「實驗期間 ≥ 22 天」「前期窗 ≥ 22 天」兩條硬門檻。若改用真正的「顧客層 λ 中位數 15.25」，下限是 **31 天**；若用間隔中位數 5，下限是 10 天。目前的 22 天是建立在一個名稱錯誤的統計量上。
- **修法**：三處改寫成「課程資料集**全體購買間隔平均 10.79 天**（`local/資料集剖析/marketing_datasets_profile.md` §Step 3 `int` 欄；間隔中位數 5 天、顧客層 λ 中位數 15.25 天）」，並明確選一個口徑當「購買週期」再重算門檻；第 478 行的出處由 `17 §4.1` 改成 profile 的正確節次。順帶在 17 §四補上這三個統計量，讓交叉引用有東西可指。
